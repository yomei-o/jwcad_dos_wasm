### 測ったものが「Ctrl を押しながら測ったもの」だった

2026-09-18 まで、エミュレータが `INT 16h AH=12h`（拡張シフト状態）に
答えていませんでした。JW_CAD は Microsoft C の `int86()` 越しに呼ぶので、
答えないと呼び出し側の `union REGS` に残っていた値がそのまま帰ります。
それが `0x94`——**Ctrl のビットが立った状態**でした。
**この repo の測定は全部、Ctrl を押しながら測ったものでした。**
直した（dosv_emu_cpp `f5da352`）ところ、合っていたはずの検査が 3 つ崩れました:

* **数え箱の横の言葉（`src/snap.h` の 17 桁目・22 桁目）は
  「修飾キーを押している間」だけ出ます。** 何も押していなければ本物は
  17 桁目に空白を書いて帯は真っ黒のままです。`JwUi.ctrl` で塞いであります
  （移植はまだ修飾キーを受け取らないので、常に 0）
* **追加･除外 の探索は書込みのペン・線種で絞りません。** 絞るのは
  修飾キーを押したときだけです。`tools/mkpick.py` の `bytes` 図面 12 本は
  **全部拾えます**（`mods ctrl` を入れると線種 2 と ペン 5 の 2 本が落ちる）。
  「SAMPLE6 はペン 4 で書いているから壁が拾えない」という説明は嘘でした——
  拾えます
* **複写・移動 の ①ﾏｳｽ位置 が通らなかった**のもこれです（4.9e）

**教訓**: エミュレータが答えていない BIOS 呼び出しがあると、
「本物はこう振る舞う」という測定が丸ごと別物になります。合わない所を
移植の側だけで説明しにいく前に、**エミュレータが何に答えていないか**を
`DOSEMU_KBD_TRACE` や `DOSEMU_MOUSE_TRACE` で見ること。
修飾キーは `mods shift` / `mods ctrl` / `mods alt` / `mods none` で
流し込めるようになっています。[SHIFT] と [GRPH] はまだ測っていません。

**`DOSEMU_WATCH` は書き方で見えるものが変わります。**
`+seg:off` の相対指定だと CPU 側（`lin()` を通る読み書き）しか鳴らず、
`[write]` の行——Memory 側が報せる書き込み——は**出ません**。
絶対番地（`DOSEMU_WATCH=3642E-3642F`）で書くと両方鳴ります。
相対指定のまま「誰も書いていない」と結論して 1 時間溶かしました。
どちらも **stdout** に出ます（`dump` は stderr）。

**回っている最中に `tests/*.exe` を建て直さないこと。** `tools/` を触るなと
同じ話ですが、こちらのほうが気づきにくい——検査は走りながら移植の実行ファイルを
呼ぶので、途中で入れ替わると**前半と後半で違うものを測った結果**が出ます。
2026-09-20 に踏みました: 面取の 1 回目が 71 画素違うという結果が出て、
直したはずの箇所を疑って探し、実は「検査の最中に別の命令のために建て直した」
だけでした（そのときの差は本物）。`sh tools/check.sh` を回している間は
`src/` も `tests/` も触らないこと。

**回っている最中の shell script を書き換えないこと。** `sh` は台本を
実行しながら読むので、途中で中身がずれると `unexpected EOF` や
`command not found` で落ちます。`sh tools/check.sh` は 50 分ほどかかるので、
その間に `tools/check.sh` や `tools/copynum.sh` を直すと**検査が途中で
死にます**（2026-09-18 に 2 回やりました）。回すときは
`cp tools/check.sh tmp/check_run.sh && sh tmp/check_run.sh` のように
写しを回すか、終わるまで触らないこと。

**`set -e` の下では `[ -n "$X" ] && …` が枝の最後に来ると危ない。**
X が空だとテストが偽 → 枝の最後の命令が偽 → **script がそこで黙って
終わります**。`tools/copynum.sh` がそうなって、本物を動かさないまま
古い撮影と比べて「241 画素違う」と言い続けました。`if [ -n … ]; then … fi`
で書くこと。

**`DOSEMU_WATCH` の当たりは標準出力**です（「watching …」だけが標準エラー）。
`2>&1 >/dev/null` にすると当たりが消えて「誰も書いていない」という嘘の
結論が出ます。

**python でソースを書き換えるとき、`open(p,'w')` は開いた瞬間に中身を
消します。** `encoding='latin-1'` で開いて日本語のコメントを含むソースを
書き戻すと `UnicodeEncodeError` が飛び、**ファイルが 0 バイトで残ります**。
2026-09-17 に `src/ui.c` と `src/typed.h` を 2 回そうしました
（`git checkout` で戻せますが、その回の書きかけは消えます）。ソースは
**utf-8 で読み書きするか、バイトのまま**触ること。書き換えは
`open(p,'rb')` → 置換 → `open(p,'wb')` がいちばん安全です。


**MZ ヘッダの「再配置 0 個」を真に受けない。** 7000 個の far 参照があるはずの
マルチセグメントのプログラムが再配置を持たない、というのは EXEPACK の徴です。
エントリ `34ab:0010` にあるのは展開スタブでした。`tools/unexepack.py` に
詳しく書いてあります。

**Ghidra はイメージをリンク時より `0x1000` セグメント上に置く。** `main` は
リンク時 `0000:0446`、Ghidra では `1000:0446`。オーバーレイの穴は
`tools/overlays.py` では `2ab8`、Ghidra では **`3ab8`** です。ここを間違えると
「オーバーレイの関数」として出てくるのは実際にはルートのコードで、
しかも 95 個ほど出てくるので、間違いに気づけません（一度やりました）。

**`INT 3Fh` の後ろ 3 バイトは命令ではない。** オーバーレイ呼び出しは
`cd 3f <番号> <オフセット 2 バイト>` の 4 バイトのトラップで、Ghidra は
そのまま操作数を命令として食べ続けます。直さないと、**オーバーレイを呼ぶ関数は
最初の呼び出し以降ぜんぶ壊れます。** `main` の生の出力がその見本で、
`swi(0x3f)` のすぐ後ろに `*(int *)(&stack0x0059 + unaff_DI) = ... + in_BX;`
のような、どこにも存在しない計算が現れます。
`tools/ghidra_scripts/MarkOverlayThunks.java` が、操作数をデータにして
フォールスルーを `+5` に飛ばし、呼び出し先に参照を張ります。

**オーバーレイの関数はバイト列を見ても始まりが分からない。** 入口はぜんぶ
`INT 3Fh` のトラップ経由で、そのトラップはルートと *他の* オーバーレイにあります。
どちらも解析中のイメージには入っていないので、`tools/thunks.py` で
ファイル全体から集めて `decomp/entries/NN.txt` に渡します。

**空のオーバーレイの穴に呼び出し参照を張らない。** サンクの飛び先に
`RefType.UNCONDITIONAL_CALL` を張ると Ghidra はそこに関数を作ります。
ところがルート単体を解析するとき穴は空（ゼロ）なので、1 バイトの関数が
ゼロの海をひとつの巨大な基本ブロックとして逆コンパイルし、**1 個あたり
約 1 MB の C** になります。ルートの `all.c` が 5.9 MB から 20 MB に膨らんで
気づきました。同じことが結合イメージでも起きます——載っているのは 1 個だけなので、
**別のオーバーレイ宛てのサンク**の飛び先は、常駐しているオーバーレイの
命令の途中を指してしまい、本物の関数を分断します（オーバーレイ 19 の
`all.c` が 14 MB になりました）。なので `MarkOverlayThunks` には
「穴に何が載っているか」を渡して、その番号宛てのサンクにだけ参照を張ります。

**VGA の書き込みモードは 1 つではない。** 線（`FUN_20a9_0732`）はモード 0 ＋
Set/Reset で色を送り、CPU が書くバイトは捨てられます。ところが円弧の画素
（`FUN_20a9_075c`）は **モード 2**（`out(0x3ce,0x0205)`）で、CPU が書く
バイトの下位 4 ビットがそのまま色になります。片方だけ実装すると、線は
正しいのに円弧だけ色が化けます。

**`-postScript` に空文字列の引数を渡さない。** `analyzeHeadless` はそこで
そのスクリプトの引数収集をやめ、**後ろに続く `-postScript` ごと黙って捨てます**。
`-postScript MarkOverlayThunks post 0 "" 0 -postScript DecompileAll ...` と
したら、解析は最後まで走ってログも正常なのに出力が一つも出ませんでした
（しかも `wc -l` が古い `index.csv` を読んで「624 行」と報告するので、
成功したように見えます）。渡すものが無いときは `-` を置きます。

**Ghidra のプロジェクトディレクトリ名を `.` で始めない。**
`Path element starting with '.' is not permitted` で落ちます（`decomp/.ghidra`
にしていて落ちました。いまは `decomp/ghidra_proj`）。

**展開した EXE にオーバーレイを繋ぐときは 512 バイト境界を守る。**
オーバーレイマネージャはルートのイメージ末尾を 512 に切り上げた位置から
MZ の連鎖を歩くので、詰め物を入れ直さないと 36 個全部が行方不明になります。

### src/cmd.c の「汎用取り消し」節が ESC を先取りする

`jw_cmd_key` の途中（8500 行台）に `if (key == 27) { … if (!c->pressed ||
c->escaped) return 0; … }` という、どの命令にも共通の「何も持っていない
ときの ESC は何もしない」節があります。中は命令ごとの分岐もいくつか
ありますが、どれにも当たらなければ**無条件で `return 0;`** します。

新しい命令固有の ESC 処理を、この節より**あとの行**（ファイルの下の方）
に書くと、`c->pressed == 0` のとき（入力欄を打っている途中はだいたい
そう）は必ずこの節に先に捕まり、書いた分岐まで決して落ちてきません
—— コンパイルは通り、関数は存在するのに、実機でキーを押しても何も
起きないという静かな失敗になります（多角形 ②正多角形 の角数入力欄の
[ESC] で踏んだ、10-06 夜）。

**対策**：命令固有の ESC 処理はこの汎用節より**前**に書く。すでに動いて
いる同種の処理（＋/／/□/○/（ の `ask_kind` 系 ESC）もこの節より前に
あるので、位置に迷ったらそこに合わせる。書いた直後は
`fprintf(stderr, …)` を要所に仕込んで実際に通ったか確認するのが早い
（今回はそれで初めて気づいた）。

### 「範囲ごと戻す」汎用節は、複写・移動では 1 段ずつ戻す場面を丸ごと飲む

上の罠とは別の落とし穴。`if (JW_RANGE(c)) { … c->pressed = 0; c->stage =
0; free(c->sel_line); … }` という節は 消去・変形・図形 など「範囲を
確定したら話は一段だけ」という命令には正しいのですが、**複写・移動は
範囲確定のあとも 段 3(追加･除外)→4(①〜⑦の一覧)→5(基準点)→6(置く場所)
→9(再配置待ち) と何段も続きます**。この汎用節は `c->pressed` が
真でありさえすれば（複写・移動は範囲を確定した時点で `pressed=2` の
まま、段が進んでも触らないので終始真）**どの段でも無条件に一致して
しまい**、段 4/5/6/7(数値欄で打っている途中)/9 のどこで [ESC] を
押しても範囲ごと（追加･除外 で選んだ中身まで）丸ごと捨てていました
（段 9 は `place_undo` で直前の 1 回だけは戻していましたが、そのあと
やはり丸ごと捨てていました）。実機は 1 段ずつしか戻りません
（9→6 は直前の 1 回を戻してから、7→4・6→5・5→4・4→3 はただ戻るだけ。
3→0 だけは実機も範囲ごと捨てるので、そこは直さなくて正解）。

**対策**：複写・移動のように範囲確定後に段がいくつも続く命令では、
汎用の「範囲ごと戻す」節に落ちる前に、段ごとの「ESC は一段戻るだけ」
を `JW_MOVE_CMD(c->command) && c->stage == N` で先に拾う（2026-10-06
深夜、`tools/steps_table.py`/`node tools/cmdstate.mjs` で段番号を
実測して見つけた。画面の文字列だけ見ていると「同じ行が出た」ようにも
見えてしまうので、`cmd.stage` の数値で確かめるのが早い）。

### 「確認の積み」を中止・取り消しが忘れる（消去 `erase_again`）

上の二つとは違う罠。消去の確認画面 `復活出来ません |①実行|②中止|` は、
左を一度押すと即座には消さず `消去 再度(L)` の状態（`c->erase_again`）に
進み、**もう一度**左を押して初めて消す——二度押しで確定する仕組み。
ところがこの「積み」を戻すのは [ESC] と ②中止 の**二つの別経路**
（前者は `jw_cmd_key` の「範囲ごと戻す」節、後者は `jw_cmd_top` が呼ぶ
`cmd_top` の `item == 2` 節——数字キー `2` も `src/main_wasm.c` の
digit→`jw_click` 変換でここに来る）で、**どちらも `c->erase_again` を
0 に戻していなかった**。結果、確認画面で一度押してから [ESC]（か
②中止）で引き返し、同じ消去をもう一度確認画面まで進めると、**最初の
一押し目でいきなり消えてしまう**（本来は二押し目でなければ消さない）。
測定：`30 216 left|150 130 left|245 170 right|160 150 left|key esc|
150 130 left|245 170 right|160 150 left` で本物は 43 本のまま、直す前の
移植は 40 本（tools/cases/probe_erase.txt
`er_escbug_no_premature_delete`、本物との突き合わせは tools/functest.sh）。

**対策**：「二度押しで確定する」類の確認フラグは、それを**降ろす
経路が複数ある**（[ESC] だけでなく、同じ意味の別のボタン・別のキーの
押しも）ことを疑うこと。片方だけ直すと、直したはずのバグがもう片方の
経路からそのまま踏める。src/cmd.c では [ESC] の節と `item == 2` の節、
両方に `if (c->command == 25) c->erase_again = 0;` を足した。

**直したあとに気づいた分かれ目**：②中止 経路はこれで本物と最後まで
一致する（やり直し後、ふつうに 2 回押せば消える）。ところが **[ESC]**
経路は、1 回目の押しで消えない（症状は直った）ところまでは一致するが、
本物はそのあと**2 回・3 回押しても 1 本も消えない**（`erase_again` を
戻す以上の何かを本物の [ESC] は変えているらしい）のに対し、移植は
ふつうに 2 回で消してしまう——つまり「最初の症状は直ったが、[ESC] 経路
だけ、直した先の状態が本物とは完全には一致していない」。decomp を見ずに
ここを埋めると当てずっぽうになるので、`tools/cases/probe_erase.txt` の
`er_escbug_open_question_no_delete_even_after_3_clicks` として**未解決の
まま**残してある（nokori.md 参照）。「症状が消えた＝完全に直った」とは
限らない、という教訓として書いておく。
