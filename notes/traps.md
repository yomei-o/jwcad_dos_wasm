### 測ったものが「Ctrl を押しながら測ったもの」だった

2026-09-18 まで、エミュレータが `INT 16h AH=12h`（拡張シフト状態）に
答えていませんでした。JW_CAD は Microsoft C の `int86()` 越しに呼ぶので、
答えないと呼び出し側の `union REGS` に残っていた値がそのまま帰ります。
それが `0x94`——**Ctrl のビットが立った状態**でした。
**この repo の測定は全部、Ctrl を押しながら測ったものでした。**
直した（dosv_emu_cpp `f5da352`）ところ、合っていたはずの検査が 3 つ崩れました:

* **数え箱の横の言葉（`src/snap.h` の 17 桁目・22 桁目）は
  「修飾キーを押している間」だけ出ます。** 何も押していなければ本物は
  17 桁目に空白を書いて帯は真っ黒のままです。`JwUi.ctrl` で塞いであります
  （移植はまだ修飾キーを受け取らないので、常に 0）
* **追加･除外 の探索は書込みのペン・線種で絞りません。** 絞るのは
  修飾キーを押したときだけです。`tools/mkpick.py` の `bytes` 図面 12 本は
  **全部拾えます**（`mods ctrl` を入れると線種 2 と ペン 5 の 2 本が落ちる）。
  「SAMPLE6 はペン 4 で書いているから壁が拾えない」という説明は嘘でした——
  拾えます
* **複写・移動 の ①ﾏｳｽ位置 が通らなかった**のもこれです（4.9e）

**教訓**: エミュレータが答えていない BIOS 呼び出しがあると、
「本物はこう振る舞う」という測定が丸ごと別物になります。合わない所を
移植の側だけで説明しにいく前に、**エミュレータが何に答えていないか**を
`DOSEMU_KBD_TRACE` や `DOSEMU_MOUSE_TRACE` で見ること。
修飾キーは `mods shift` / `mods ctrl` / `mods alt` / `mods none` で
流し込めるようになっています。[SHIFT] と [GRPH] はまだ測っていません。

**`DOSEMU_WATCH` は書き方で見えるものが変わります。**
`+seg:off` の相対指定だと CPU 側（`lin()` を通る読み書き）しか鳴らず、
`[write]` の行——Memory 側が報せる書き込み——は**出ません**。
絶対番地（`DOSEMU_WATCH=3642E-3642F`）で書くと両方鳴ります。
相対指定のまま「誰も書いていない」と結論して 1 時間溶かしました。
どちらも **stdout** に出ます（`dump` は stderr）。

**回っている最中に `tests/*.exe` を建て直さないこと。** `tools/` を触るなと
同じ話ですが、こちらのほうが気づきにくい——検査は走りながら移植の実行ファイルを
呼ぶので、途中で入れ替わると**前半と後半で違うものを測った結果**が出ます。
2026-09-20 に踏みました: 面取の 1 回目が 71 画素違うという結果が出て、
直したはずの箇所を疑って探し、実は「検査の最中に別の命令のために建て直した」
だけでした（そのときの差は本物）。`sh tools/check.sh` を回している間は
`src/` も `tests/` も触らないこと。

**回っている最中の shell script を書き換えないこと。** `sh` は台本を
実行しながら読むので、途中で中身がずれると `unexpected EOF` や
`command not found` で落ちます。`sh tools/check.sh` は 50 分ほどかかるので、
その間に `tools/check.sh` や `tools/copynum.sh` を直すと**検査が途中で
死にます**（2026-09-18 に 2 回やりました）。回すときは
`cp tools/check.sh tmp/check_run.sh && sh tmp/check_run.sh` のように
写しを回すか、終わるまで触らないこと。

**`set -e` の下では `[ -n "$X" ] && …` が枝の最後に来ると危ない。**
X が空だとテストが偽 → 枝の最後の命令が偽 → **script がそこで黙って
終わります**。`tools/copynum.sh` がそうなって、本物を動かさないまま
古い撮影と比べて「241 画素違う」と言い続けました。`if [ -n … ]; then … fi`
で書くこと。

**`DOSEMU_WATCH` の当たりは標準出力**です（「watching …」だけが標準エラー）。
`2>&1 >/dev/null` にすると当たりが消えて「誰も書いていない」という嘘の
結論が出ます。

**python でソースを書き換えるとき、`open(p,'w')` は開いた瞬間に中身を
消します。** `encoding='latin-1'` で開いて日本語のコメントを含むソースを
書き戻すと `UnicodeEncodeError` が飛び、**ファイルが 0 バイトで残ります**。
2026-09-17 に `src/ui.c` と `src/typed.h` を 2 回そうしました
（`git checkout` で戻せますが、その回の書きかけは消えます）。ソースは
**utf-8 で読み書きするか、バイトのまま**触ること。書き換えは
`open(p,'rb')` → 置換 → `open(p,'wb')` がいちばん安全です。


**MZ ヘッダの「再配置 0 個」を真に受けない。** 7000 個の far 参照があるはずの
マルチセグメントのプログラムが再配置を持たない、というのは EXEPACK の徴です。
エントリ `34ab:0010` にあるのは展開スタブでした。`tools/unexepack.py` に
詳しく書いてあります。

**Ghidra はイメージをリンク時より `0x1000` セグメント上に置く。** `main` は
リンク時 `0000:0446`、Ghidra では `1000:0446`。オーバーレイの穴は
`tools/overlays.py` では `2ab8`、Ghidra では **`3ab8`** です。ここを間違えると
「オーバーレイの関数」として出てくるのは実際にはルートのコードで、
しかも 95 個ほど出てくるので、間違いに気づけません（一度やりました）。

**`INT 3Fh` の後ろ 3 バイトは命令ではない。** オーバーレイ呼び出しは
`cd 3f <番号> <オフセット 2 バイト>` の 4 バイトのトラップで、Ghidra は
そのまま操作数を命令として食べ続けます。直さないと、**オーバーレイを呼ぶ関数は
最初の呼び出し以降ぜんぶ壊れます。** `main` の生の出力がその見本で、
`swi(0x3f)` のすぐ後ろに `*(int *)(&stack0x0059 + unaff_DI) = ... + in_BX;`
のような、どこにも存在しない計算が現れます。
`tools/ghidra_scripts/MarkOverlayThunks.java` が、操作数をデータにして
フォールスルーを `+5` に飛ばし、呼び出し先に参照を張ります。

**オーバーレイの関数はバイト列を見ても始まりが分からない。** 入口はぜんぶ
`INT 3Fh` のトラップ経由で、そのトラップはルートと *他の* オーバーレイにあります。
どちらも解析中のイメージには入っていないので、`tools/thunks.py` で
ファイル全体から集めて `decomp/entries/NN.txt` に渡します。

**空のオーバーレイの穴に呼び出し参照を張らない。** サンクの飛び先に
`RefType.UNCONDITIONAL_CALL` を張ると Ghidra はそこに関数を作ります。
ところがルート単体を解析するとき穴は空（ゼロ）なので、1 バイトの関数が
ゼロの海をひとつの巨大な基本ブロックとして逆コンパイルし、**1 個あたり
約 1 MB の C** になります。ルートの `all.c` が 5.9 MB から 20 MB に膨らんで
気づきました。同じことが結合イメージでも起きます——載っているのは 1 個だけなので、
**別のオーバーレイ宛てのサンク**の飛び先は、常駐しているオーバーレイの
命令の途中を指してしまい、本物の関数を分断します（オーバーレイ 19 の
`all.c` が 14 MB になりました）。なので `MarkOverlayThunks` には
「穴に何が載っているか」を渡して、その番号宛てのサンクにだけ参照を張ります。

**VGA の書き込みモードは 1 つではない。** 線（`FUN_20a9_0732`）はモード 0 ＋
Set/Reset で色を送り、CPU が書くバイトは捨てられます。ところが円弧の画素
（`FUN_20a9_075c`）は **モード 2**（`out(0x3ce,0x0205)`）で、CPU が書く
バイトの下位 4 ビットがそのまま色になります。片方だけ実装すると、線は
正しいのに円弧だけ色が化けます。

**`-postScript` に空文字列の引数を渡さない。** `analyzeHeadless` はそこで
そのスクリプトの引数収集をやめ、**後ろに続く `-postScript` ごと黙って捨てます**。
`-postScript MarkOverlayThunks post 0 "" 0 -postScript DecompileAll ...` と
したら、解析は最後まで走ってログも正常なのに出力が一つも出ませんでした
（しかも `wc -l` が古い `index.csv` を読んで「624 行」と報告するので、
成功したように見えます）。渡すものが無いときは `-` を置きます。

**Ghidra のプロジェクトディレクトリ名を `.` で始めない。**
`Path element starting with '.' is not permitted` で落ちます（`decomp/.ghidra`
にしていて落ちました。いまは `decomp/ghidra_proj`）。

**展開した EXE にオーバーレイを繋ぐときは 512 バイト境界を守る。**
オーバーレイマネージャはルートのイメージ末尾を 512 に切り上げた位置から
MZ の連鎖を歩くので、詰め物を入れ直さないと 36 個全部が行方不明になります。

### src/cmd.c の「汎用取り消し」節が ESC を先取りする

`jw_cmd_key` の途中（8500 行台）に `if (key == 27) { … if (!c->pressed ||
c->escaped) return 0; … }` という、どの命令にも共通の「何も持っていない
ときの ESC は何もしない」節があります。中は命令ごとの分岐もいくつか
ありますが、どれにも当たらなければ**無条件で `return 0;`** します。

新しい命令固有の ESC 処理を、この節より**あとの行**（ファイルの下の方）
に書くと、`c->pressed == 0` のとき（入力欄を打っている途中はだいたい
そう）は必ずこの節に先に捕まり、書いた分岐まで決して落ちてきません
—— コンパイルは通り、関数は存在するのに、実機でキーを押しても何も
起きないという静かな失敗になります（多角形 ②正多角形 の角数入力欄の
[ESC] で踏んだ、10-06 夜）。

**対策**：命令固有の ESC 処理はこの汎用節より**前**に書く。すでに動いて
いる同種の処理（＋/／/□/○/（ の `ask_kind` 系 ESC）もこの節より前に
あるので、位置に迷ったらそこに合わせる。書いた直後は
`fprintf(stderr, …)` を要所に仕込んで実際に通ったか確認するのが早い
（今回はそれで初めて気づいた）。

### 「範囲ごと戻す」汎用節は、複写・移動では 1 段ずつ戻す場面を丸ごと飲む

上の罠とは別の落とし穴。`if (JW_RANGE(c)) { … c->pressed = 0; c->stage =
0; free(c->sel_line); … }` という節は 消去・変形・図形 など「範囲を
確定したら話は一段だけ」という命令には正しいのですが、**複写・移動は
範囲確定のあとも 段 3(追加･除外)→4(①〜⑦の一覧)→5(基準点)→6(置く場所)
→9(再配置待ち) と何段も続きます**。この汎用節は `c->pressed` が
真でありさえすれば（複写・移動は範囲を確定した時点で `pressed=2` の
まま、段が進んでも触らないので終始真）**どの段でも無条件に一致して
しまい**、段 4/5/6/7(数値欄で打っている途中)/9 のどこで [ESC] を
押しても範囲ごと（追加･除外 で選んだ中身まで）丸ごと捨てていました
（段 9 は `place_undo` で直前の 1 回だけは戻していましたが、そのあと
やはり丸ごと捨てていました）。実機は 1 段ずつしか戻りません
（9→6 は直前の 1 回を戻してから、7→4・6→5・5→4・4→3 はただ戻るだけ。
3→0 だけは実機も範囲ごと捨てるので、そこは直さなくて正解）。

**対策**：複写・移動のように範囲確定後に段がいくつも続く命令では、
汎用の「範囲ごと戻す」節に落ちる前に、段ごとの「ESC は一段戻るだけ」
を `JW_MOVE_CMD(c->command) && c->stage == N` で先に拾う（2026-10-06
深夜、`tools/steps_table.py`/`node tools/cmdstate.mjs` で段番号を
実測して見つけた。画面の文字列だけ見ていると「同じ行が出た」ようにも
見えてしまうので、`cmd.stage` の数値で確かめるのが早い）。

### 「確認の積み」を中止・取り消しが忘れる（消去 `erase_again`）

上の二つとは違う罠。消去の確認画面 `復活出来ません |①実行|②中止|` は、
左を一度押すと即座には消さず `消去 再度(L)` の状態（`c->erase_again`）に
進み、**もう一度**左を押して初めて消す——二度押しで確定する仕組み。
ところがこの「積み」を戻すのは [ESC] と ②中止 の**二つの別経路**
（前者は `jw_cmd_key` の「範囲ごと戻す」節、後者は `jw_cmd_top` が呼ぶ
`cmd_top` の `item == 2` 節——数字キー `2` も `src/main_wasm.c` の
digit→`jw_click` 変換でここに来る）で、**どちらも `c->erase_again` を
0 に戻していなかった**。結果、確認画面で一度押してから [ESC]（か
②中止）で引き返し、同じ消去をもう一度確認画面まで進めると、**最初の
一押し目でいきなり消えてしまう**（本来は二押し目でなければ消さない）。
測定：`30 216 left|150 130 left|245 170 right|160 150 left|key esc|
150 130 left|245 170 right|160 150 left` で本物は 43 本のまま、直す前の
移植は 40 本（tools/cases/probe_erase.txt
`er_escbug_no_premature_delete`、本物との突き合わせは tools/functest.sh）。

**対策**：「二度押しで確定する」類の確認フラグは、それを**降ろす
経路が複数ある**（[ESC] だけでなく、同じ意味の別のボタン・別のキーの
押しも）ことを疑うこと。片方だけ直すと、直したはずのバグがもう片方の
経路からそのまま踏める。src/cmd.c では [ESC] の節と `item == 2` の節、
両方に `if (c->command == 25) c->erase_again = 0;` を足した。

### 「消す条件」のガードが、消える物が無い段にも効いてしまう（ハッチ 残数）

上の三つとも ESC の話だったが、これは数字キーの話。ハッチは枠を 2 本以上
持つまで `残数` の数え箱そのものが画面に出ない（0〜1 本の段では桁 70 に
何も書かれない）。一方、数字キー（①自動選択 に外れたもの）を押すと
`hatch_plain` が立ち、「残数 を消す」ガード（src/ui.c の `stage_text_1` と
`jw_ui_draw` の 2 か所、どちらも「最初の行の数字で 残数 は消える」という
10-06 夜の測定 `h_n1` から来ている）が桁 70 の描画を丸ごと飛ばす。この
ガードが `hatch_n`（＝何本持っているか）を見ていなかったため、**残数が
まだ無い段（hatch_n<2）だけでなく、残数が出ている最中（hatch_n>=2）にも
効いてしまい**、枠を 2 本以上持ってから数字キーを押すと本物にはない
「残数が消える」症状が出た（本物は hatch_n>=2 でも数字キーで残数は
消えない、tools/probe.sh で確認）。`h_n1`〜`h_n3` の測定は全部 hatch_n が
0 か 1 の段でしか取っていなかったので、このガードは「残数が無い段で
何も描かない（無害）」という前提のまま「残数がある段でも効く」という
副作用を長らく持っていた——既存の func_all（hatch_s0_c1〜c9・hatch_s1_c1
〜c9）はどれも hatch_n<2 の段しか押さないので、素通りして気づかれずにいた。

**対策**：「◯◯を消す／描かない」系のガードを足すときは、測定した場面
（この場合は hatch_n<2）の外でもそのガードが生きたままにならないか、
条件そのものに測定した場面の境界（`s->hatch_n < 2` のような）を書き込む
こと。症状が無かったからといって副作用が無いとは限らない——ここは
2 本以上持ってから数字キーを押す組み合わせが、今回の総当たり監査
（nokori.md A節）で初めて試されるまで 1 か月近く誰も踏んでいなかった。
functest（保存ファイルの記録）はこの種の画面だけの差を一切捕まえない
ので、tools/seqshot.mjs + tools/rawpng.py で画面そのものを見比べること。

### 一本道の「直近の undo」を本数で決め打ちすると、途中で片方が消えたときに巻き添えを出す（線消 部分消去の [ESC]）

線消 部分消去（左押しで線の一部だけ消す）は、切った残り（破片、0〜2 本）を
末尾に足し、元の線は抜く。[ESC] が「破片を消して元の線を戻す」ことを実機で
確かめ（`tools/functest.sh '90 216 left' '400 140 left' '300 250 left'
'450 330 left' 'key esc'`、本物は破片 2 本が消えて元の形 1 本だけに戻る）、
最初は「`ld_undo_n` 本だけ末尾から `jwc_remove_line` する」という実装にした。

ところが `tools/cases/func_all.txt` の `linedel_s1_c1`（同じ線を続けて
①線切断寸法 の欄を開いたあと、間に**右押しの全消**を挟んでから [ESC]）で
試すと壊れた——右押しの全消が破片の片方を**先に**取り去っていて、
「末尾から N 本」が破片でも何でもない無関係な行を巻き添えに消していた。
`linedel_s1_c1` は nokori.md に「現状の挙動で一致しているので触らない」と
書いてあった既存の合格ケースで、新しい修正がそれを壊した形。

まず「末尾から N 本」を「破片の中身（座標・種類・ペン・レイヤ）で探して
消す」に直したが、これでも `linedel_s1_c1` は直らなかった——実機を
`fprintf(stderr, …)` で内部状態ごと追うと、間に右押しの全消を挟んだときの
本物は**そもそも破片を消していない**（元の線だけが追加で戻り、破片は
そのまま残る）ことが分かった。実機の undo は「直近の一操作」を戻すはずが、
右押しの全消という**別の undo 経路**（`rd_undo`）が割り込むと、部分消去の
ほう（`ld_undo`）の戻し方自体が変わる——「本数で決め打ち」も「中身一致」も、
どちらも「他の undo 経路が割り込んでいない」ことを前提にしていた。

**対策**：`c->rd_undo_on`（間に別の undo 経路が割り込んだか）を見てから
破片を消すかどうかを決める——割り込んでいなければ消す、割り込んでいれば
旧来どおり消さない（`src/cmd.c` の線消 ESC、2026-10-07 深夜）。「直近の
一操作の undo」を実装するときは、**同じコマンドの中に別の undo 経路が
もう一つあるかどうか**を先に確認すること。あればその経路が動いた形跡
（ここでは `rd_undo_on`）を分岐の条件に入れないと、「決め打ちの本数」も
「中身一致の検索」も、どちらも巻き添えを出し得る。

**直したあとに気づいた分かれ目**：②中止 経路はこれで本物と最後まで
一致する（やり直し後、ふつうに 2 回押せば消える）。ところが **[ESC]**
経路は、1 回目の押しで消えない（症状は直った）ところまでは一致するが、
本物はそのあと**2 回・3 回押しても 1 本も消えない**（`erase_again` を
戻す以上の何かを本物の [ESC] は変えているらしい）のに対し、移植は
ふつうに 2 回で消してしまう——つまり「最初の症状は直ったが、[ESC] 経路
だけ、直した先の状態が本物とは完全には一致していない」。decomp を見ずに
ここを埋めると当てずっぽうになるので、`tools/cases/probe_erase.txt` の
`er_escbug_open_question_no_delete_even_after_3_clicks` として**未解決の
まま**残してある（nokori.md 参照）。「症状が消えた＝完全に直った」とは
限らない、という教訓として書いておく。

### 「あとで 0 に戻す」memset が、途中の関数呼び出しが付けた印まで消す（線消 dot_mark）

線消 部分消去で切った残りの線を `jwc_add_line` で足したあと、昔のコードは
`memset(新しい線.rest + 1, 0, 3)` で rest[1]〜rest[3] を丸ごと 0 にしていた
（「rest は 0（測定）」というコメント付きで）。ところが `jwc_add_line` は
内部で `dot_mark()`（src/jwc.c、短すぎる線に rest[2] の bit 0x10 を立てる、
21f2:2750 decomp 済み）を呼んでいて、切った残りがたまたま点扱いになるほど
短い（dx<1・dy<1）ときはこの bit が正しく立っていた。それを後ろの memset が
無条件に消していた——「測定で rest は 0 だった」が、それは測定した具体例が
たまたま点扱いにならない長さの線だったからで、**短い残りでは 0 ではない**
ことを見落としていた（func_all `linedel_s1_c1`、線 28、(161.973,139.943)-
(162.000,139.943) で顕在化）。

**対策**：呼んだ関数（ここでは `jwc_add_line`）がすでに正しく計算した
フィールドを、あとから「0 に決め打ち」で上書きしないこと。測定で「0 だった」
という結果は、測定した具体例の条件（ここでは線の長さ）が変わっても同じとは
限らない。rest[1]・rest[3] だけを個別に 0 にし、rest[2]（dot_mark が触る
フィールド）には触らないように直した。

### 円・曲線の「置いた直後の [ESC]」は 1 回では終わらない（2 回目で完全に抜けて、それまでの全部を取り消す）

多角形 ②正多角形・（ ①三点指示 では「置いた直後の [ESC] は直近の 1 回だけ
取り消し、2 回目は無反応」という形だったので、○ ②楕円・曲線 ⑥連続弧 も
同じだろうと思い込みそうになったが、実測すると **2 回目の [ESC] も効き、
しかも「連続弧ごと／楕円ごと完全に抜ける」挙動**だった：

* ○ ②楕円：楕円を確定 → 次の楕円の中心だけ取って [ESC]（中心を捨てるだけ、
  楕円は 1 個のまま）→ もう一度 [ESC] で**確定していた楕円も消え、○ の
  トップへ完全に抜ける**（そのあと項目②を選び直すまで押しは無反応）。
* 曲線 ⑥連続弧：2 本目を [ESC] で戻すと 1 本目だけ残る（ここまでは多角形と
  同じ）が、**その状態でもう一度 [ESC] を押すと 1 本目も消えて連続弧から
  完全に抜ける**。

どちらも「対象ごとに 1 回だけ戻せる」のではなく、**直前に確定した 1 個を
戻すところまでは同じ仕組みで何段でも戻れて、戻し切ったら持ち場（モード）
そのものから抜ける**という形だった。既存コードは「戻し切ったらそこで
何もしない」と決め打ちしていた（○ は `ell_done` を 0 に戻すだけ、連続弧は
`ch_n>0` の条件で 2 回目以降を素通りさせるだけ）ため、戻し切ったあとの
もう一押しで消えるはずの最後の 1 個が残っていた。

**対策**：「このコマンドは 1 回しか戻せない」という結論を、違うコマンドへ
そのまま持ち込まないこと。似た ESC の形でも、**戻し切った先で何が起きるか
（何も起きない／最後の 1 個も消えて抜ける）は command ごとに別に測る**。
ここでは `tools/functest.sh` で ESC を 1 回・2 回・2 回+クリック、と段階的に
手数を増やして記録バイト列を比べ、「2 回目で消える」「消えたあとは項目を
選び直すまで無反応」の両方を確認した（func_all `circle_s0_c2`・
`curve_s1_c6`）。

### 「複写・移動と同じ形だろう」という思い込みは測らないと分からない（線変更 の 絞り込み／変更内容）

複写・移動で見つけた「範囲確定のあとも段がいくつも続く命令は、汎用の
『範囲ごと戻す』節に落ちる前に 1 段ずつ戻る規則を足す」という教訓を、
同じく範囲確定のあとに段が続く**線変更 ①指定範囲内変更**（3:追加･除外→
2:絞り込み→4:変更内容）にもそのまま適用できるはずだと疑って監査したが、
**実測すると線変更は複写・移動と違い、どちらの段でも範囲ごと丸ごと
捨てるのが本物の正しい挙動**だった（消去と同じ「範囲確定のあとは段が
もう無い」パターンに近く、複写・移動だけが例外的に多段だった）。
確認方法：ESC のあとに箱を再指定せず `type 1|type 3|type 1`（絞り込み→
変更内容→適用のつもりの押し）を打っても、本物・移植とも rest の印
（近傍読取の触れた跡）しか動かず、肝心の `type=`/`pen=`/`lay=` は
変わらない——つまり「絞り込み」や「変更内容」の段へは戻っておらず、
箱の取り直し（段 0）からやり直しになっている、という間接証拠。
`tools/functest.sh` は保存ファイルの記録しか見ないので、ESC の着地点を
直接は見られない。「ESC のあとに続く押しが実際に何を達成できるか」で
間接的に着地段を当てるのがこの種の監査の基本形（nokori.md escaudit5）。

**対策**：似た構造（範囲確定後に段が続く）を見つけても、「前に別の
コマンドで見つけた規則がここにも当てはまるはず」と決め打ちしない。
必ず実測し、一致しなければそれはそれで「バグではなかった」と記録する
——バグを探しに行って「バグが無かった」と結論するのも立派な監査結果。

### 「選び直しても残る」変数の仲間を見落とす（線変更 ②レイヤ変更【有】/【無】）

`jw_cmd_pick`（命令を選ぶたびに呼ばれ、`memset(c, 0, sizeof(*c))` で
`JwCmd` を丸ごと初期化する）には、＋/／の長さ・角度や□の縦横など
「選び直しても消えない」値を memset の前に `keep_` ローカル変数へ
退避し、あとで書き戻す仕組みが**最初から用意されている**（DGROUP 側の
記憶を真似たもの）。ところが線変更 ②レイヤ変更【有】/【無】
（`c->lc_off`）はこの仕組みに入っていなかった——decomp 的には同じ
DGROUP 側の記憶（`DS:[0x5e40]`、既存コメントに引用済み）なのに、
実装では「ただの `JwCmd` のフィールド」として扱われていたため、
命令を選び直す（同じ線変更をもう一度選ぶだけでも、間に別の命令を
挟んでも）たびに memset で【有】に戻ってしまっていた。

### [BS] は「打った文字数」を戻すだけとは限らない（寸法 ⑧値変 の数値欄）

多くの欄の [BS]（＋/／/□/○ の `寸法=`・`半径=`・`角度=` など）は
「打った文字（`c->typed`/`typed_n`）を一つ減らすだけで、まだ打って
いない残りはそのまま」という単純な classic backspace で、既存実装も
その形だった。寸法 ⑧値変 の段 8（拾った既存の寸法値を上書きする欄）も
同じ形だろうと決め打ちしたが、実測すると違った：`250` を拾って `99` と
打つと（上書きなので）`990`（ここまでは単純な「打った分だけ上書き、
届かない残りはそのまま」で合う）。ところがここで [BS] を一回押すと、
本物は `90`（`typed_n` だけ一つ減らして残り `50` を付け直す旧実装の
想定なら `950` になるはず）。`9` だけ打って [BS] 一回でも `50`
（無変更の `250` に戻るのではない）。

つまり [BS] は「カーソルの直前の 1 文字を、**欄が今見せている文字列
全体**からまるごと削って詰める」という、ふつうのテキスト欄の
backspace だった——「打った文字」と「まだ届いていない元の文字列の
残り」を別々に持って front 側だけ戻す、という今までの欄の形とは別物。
`JwCmd` に欄の「今の表示」をまるごと持つ生きたバッファ（`dim_val_buf`）
とカーソル（`dim_val_pos`）を足し、digit は上書き／[BS] はカーソルの
直前の 1 文字を文字列から削って詰める、という素直な実装に直した
（escaudit6、tools/cases/probe_dim_val.txt）。

**対策**：「似た見た目の欄だから同じ [BS] の規則だろう」と決め打ちしない
こと。**[BS] を一回だけでなく、文字を複数打ってから押す・1 文字だけ
打ってから押す、の両方を実測して**、結果の文字列の「長さ」が単純な
「打った分を一つ減らす」モデルと合うかを確認する（長さが合わなければ、
それは「カーソル位置を戻すだけ」ではなく「表示全体から 1 文字削る」
モデルを疑う）。

### 帯のセルを押しても「選んだ」ことにならない（変形 ①パラメトリック変形）

変形（17）の最初の行は、ほかの命令の「①②③…」のような升クリックでは
なく、**左右どちらのボタンで押すかだけ**でモードが決まる仕組み
（src/cmd.c:18588、`!c->again && !c->hen_env && !c->hen_dbl &&
!c->hen_kigou` の間だけ生きていて、左なら `c->again=1`・右なら
`c->hen_env=1` を一度だけ立てて抜ける）。数字キー `1` も同じ理由で
`c->again=1` を立てる（cmd.c:6994）。

ところが帯の①パラメトリック変形セル（桁9〜31、src/main_wasm.c の
`x/8+1 >= 9 && <= 31` の分岐）を押したときは、hen_dbl/hen_env/hen_kigou
を 0 に戻す（＝③④から①へ戻す）だけで、`c->again` を立てていなかった。
その結果、セルを押したあとの**最初の作図領域の押しがまだ「モード選択
前」のものとして扱われ直し**、右ボタンで範囲を閉じると誤って
②包絡処理変形に化けていた（本物は①パラメトリック変形のまま）。

**対策**：「ボタンの左右だけで状態を1回だけ決める」仕組み（`again` の
ような、専用フラグを持たないモード）がある命令で、同じ選択を**帯の
セルからも**できるようにするときは、セル側のハンドラにも同じ「一度だけ
立てるフラグ」を書き込むこと。セル側だけ見ると「もう選ばれている」ように
見えるが、実際にモードを**確定させる**変数（ここでは `again`）は
クリック位置ではなく別の専用フィールドにあるので、見落としやすい。
functest.sh でモード選択→範囲→基準点→置く場所、という一連の手順を
通して初めて気づいた（線が一本も動かなかった）。

### `trunc` だけの丸めは、境目の角度でちょうど外れる（面取 楕円面 自動版）

decomp の記述をそのまま `flat = trunc(10000·tan(半分))`（+0.5 無し）で実装すると、90° の角で
`tan(45°)` が倍精度では厳密に 1.0 にならず `0.9999999999999999` に丸まり、`flat` が `10000` では
なく `9999` になった。90°・R=30mm は notes に実機確認例があり（`flat=10000`、tilt=315、
start=135、end=225）、`flat` だけがそこから外れて気づいた。`trunc(10000x+0.5)` に直すと一致した。

**対策**：decomp の文字列や逆アセンブルに `trunc` とだけ書いてあっても、入力が境目の値
（45°・90° など、三角関数が理論上ちょうど整数になる角度）を取り得るなら、浮動小数の丸め誤差で
1 ずれないか境目の値で検算すること。文書の記述を疑うのではなく、**既知の実機値と最後の桁まで
突き合わせて**初めて気づけた（このケースは `tools/cases/probe_chamfer_lell.txt` の
`chamfer_ell_auto` を node 経由の WASM 実行で確認）。

### 複数セッションが同時に実機を叩くと tmp/sroot.lock が詰まる

2026-10-07 未明、複数の Claude セッションが同時に `tools/functest.sh`
（`tools/save.sh` 経由で実機を叩く）を走らせていたため、`tmp/sroot.lock`
が常に埋まっていて、30分以上どのセッションも実機との突き合わせができ
なかった（`tasklist | grep dosemu` で見えるプロセスが途切れなく入れ替
わり続ける）。**ロックが生きている間に `rmdir` で無理に外さないこと**
——外した直後に試した save が `the save did not happen` で失敗した
（他セッションの保存処理と衝突した可能性がある。実害があったかは
未確認だが、やらない方がよい）。空くまで待つか、ESC/BS の規則は
decomp（src/henkei.h・src/copy.h などの `[ESC]` 札の実機撮り）や
`tools/cmdstate.mjs`（port 内部の段遷移、実機不要）で裏取りできる分だけ
先に進め、実機突き合わせ（functest.sh）は空いたセッションに持ち越す
という判断も有り（escaudit7 で変形の段4〜7 の ESC 修正はこの方法で
「かなり確からしいが実機 100% 確認ではない」として記録した）。

**対策**：「選び直しても残る」仕組みがすでにコード中にあるコマンドで
新しいフラグを足すときは、そのフラグの decomp 根拠（固定アドレスを
読んでいるか、命令の構造体の中かどうか）を見て、固定アドレス系なら
**既存の `keep_` の仲間に入れる**こと。症状は「ESC のバグ」ではなく
「全く無関係な場面（別コマンドを挟んだ・同じコマンドを選び直した）で
勝手に設定が戻る」という形で出るので、ESC だけを疑っていると見落とす
（`tools/functest.sh` で、トグルしたあと同じコマンドを選び直すだけの
最小再現 `30 200 left|type 2|30 200 left|499 271 left` が本物との
食い違いを示した——SAMPLE6 の線 38、pen は 1→4 に変わるが lay は 00 の
まま、直す前の移植は 02 に変わっていた）。

### 共通入力関数 `2bb4:2cb4` への呼び出しが、Ghidra では別の名前で出る（`FUN_1def_0904`）

RESUME.md の「0.」にある共通入力関数は root `2bb4:2cb4`（Ghidra 名
`FUN_2bb4_2cb4`）だが、`tools/disasm.py` の生アセンブリでは
`lcall 0x1bb4, 0x2cb4`（リンク時番地、trap に既出の「Ghidra は
0x1000 セグメント上」を踏まえればこれで合っている）とはっきり出る
一方、**同じ呼び出しを `tools/func.py` で読むと `local_x =
FUN_1def_0904();` という、全く違うセグメント（1def）の名前の関数
呼び出しとして decompile される**（ovl15 3ab8:0d67・3ab8:2185 の
2 か所で確認、2026-10-07 文字 監査）。引数も見えない
（`Type propagation algorithm not settling` の警告つき）。

これは実在する別関数ではなく、オーバーレイ越しの呼び出しを Ghidra が
解決できず、たまたま近くにあった常駐関数の名前を当てただけと見られる
（`MarkOverlayThunks` 系の既知の限界の仲間）。**decompile された C で
関数名だけを見て「別の共通処理を呼んでいる」と早合点しないこと**——
呼び出し元の生アセンブリ（`tools/disasm.py --ovl N 0 0x10000` の
出力）で実際の番地が `1bb4:2cb4` かどうかを必ず確かめる。引数（ESC
を許す第 1 引数が 0 か 0x2710 か、`[0xc2c]` を呼び出し前後で 1/0 に
トグルしているか）も decompile された C では消えているので、同じ
生アセンブリから手で読み直す必要がある。

### `Buffer.from(arrayBuffer, offset, length)` は複製ではなく「窓」

WASM の画面を自前の node script で比べようとして、何回キーを押しても
前後のフレームの差分が 0 画素のまま、という偽の「無変化」に 1 時間近く
刺された（2026-10-07、□・○・円弧の数え箱の検査）。`Buffer.from(M.HEAPU8.buffer,
p, len)` は、渡した **引数が `ArrayBuffer` のときだけ**複製せずに同じ
メモリを指す窓を返す——あとから `.slice()` を呼んでも、`.slice()` 自体が
複製ではなく部分窓を返す Node の仕様なので、何も複製されない。結果、
あとで撮った「2 枚目」の実体は 1 枚目の変数と**同じ WASM メモリ**を
指したままで、どちらを見ても「いまの」画面になり、差が常に 0 になる。

`Buffer.from(typedArray)`（`ArrayBuffer` ではなく `Uint8Array` などを渡す）
だけが複製する。直すなら

```js
Buffer.from(new Uint8Array(M.HEAPU8.buffer, p, len))   // 複製される
```

**対策**：wasm のフレームバッファを複数回、時間をおいて比べる自前の
script を書くときは、`Buffer.from(arrayBuffer, offset, length)` 単体を
疑うこと。1 枚だけ撮ってすぐファイルに書く（`tools/clickshot.mjs` の形）
なら影響しないが、複数枚をメモリ上に保持して差分を取る書き方は上の
`new Uint8Array(...)` の形で複製すること。

### 「段を一つ戻す」ESC は、段番号だけでなく同じだけ進んだ別の印も戻さないと巻き戻らない（複写・移動 ③〜⑥）

複写・移動の ③数値倍率・④ﾏｳｽ倍率・⑤反転・⑥回転 は、画面に出る `c->stage`
（17〜25 あたり）とは別に、「①〜⑦のどれを選んでどこまで進んだか」を持つ
専用の変数（`c->scaling`・`c->mscale`・`c->rotate`・`c->mirror`、1〜4/5 の
カウンタ）を持っている。クリック・キー入力のハンドラは **`c->stage` では
なくこの変数を見て**どの処理をするかを決めている（例：
`if (c->rotate || c->scaling) { ... if (*state==1) {基点を取る} else if
(*state==2) {欄が持っている（クリックは捨てる）} else {配置する} }`）。

[ESC] で段を一つ戻す節（`src/cmd.c` の「複写・移動は段を一つずつ戻す」
節）は、2026-10-06 に見つかった「範囲ごと戻す汎用節に落とさない」という
教訓（上の罠）のとおり段番号は一段ずつ正しく戻していたが、**この専用変数の
ほうは一度も触っていなかった**。結果、[ESC] を複数回押して段が
20→19→18→17 と戻っても、変数は「完了」(4) のまま止まり、段17（本来は
「基準点をもう一度押してください」という画面）でクリックしても、
ハンドラは変数が4であることしか見ていないので「もう一度配置する」という
的外れな処理が起きる——古い倍率・古い基点のままもう一つ複写ができてしまい、
ひどいときはコマンドの選び直し状態（`cmd=3, stage=0` 相当）にまで化けた
（`tools/cmdstate.mjs` で再現：`type 3|200 300 left|type 2|key enter|
400 300 left|key esc|key esc|key esc|300 250 left` のあと `cmd` が変わる）。

段表だけを `tools/cmdstate.mjs` や実機の画面で確かめて「段は正しく一段
戻っている」と結論しても、**画面に出ない内部変数が一緒に戻っているかは
別に確かめないと分からない**——ここでは段の遷移そのものは既存のコメントが
指す decomp 照合済みの番地のままで、変数のほうだけが port 独自の見落とし
だった。

**対策**：「どこまで進んだか」を段番号と**別に**持つ変数（カウンタ・
フラグ）がある命令で、「ESC で段を一つ戻す」系の処理を書くときは、
その変数も段と同じ歩幅で一緒に戻すこと。段の遷移だけを実機/画面で
確認して満足せず、**戻った先で次の操作（クリック・入力）が正しい分岐に
入るか**まで通しで確かめる（`tools/cmdstate.mjs` に当該変数を出力項目
として足すと楽——今回は `jw_cmd_state()` に `mirror=%d rotate=%d
scaling=%d mscale=%d` を追加した）。

### 「段遷移だけ decomp 照合済み」は、その段で呼ぶ関数が取り消しの控えを
立てているかまでは保証しない（複写 ⑤反転・⑥回転・③数値倍率の place_undo）

上の罠のすぐ隣で見つかった、似て非なる話。`JW_RANGE` の ESC 節には
「置いた直後の [ESC] は直前の置きを取り消してから一段戻る」という
decomp 照合済みの規則があり、`place_undo(c, d)` を呼ぶコードも既に
あった。ところが `place_undo` は `c->mv_undo`（立っているときだけ動く
一回限りのフラグ）と `c->mv_nl` 等（取り消す基準になる「直前の件数」の
控え）を見るだけで、**その控えを立てるのは `place_by`（①ﾏｳｽ位置・
②数値位置 の置き）だけ**だった。⑤反転・⑥回転・③数値倍率・④ﾏｳｽ倍率 は
`mirror_range`/`turn_range`/`scale_range` を `place_by` を経由せず直接
呼ぶので、置いても `mv_undo` が一度も立たず、**ESC 節のコードは実行
されるのに中身（place_undo）は何もしていなかった**——段番号だけは
正しく一つ戻るので、`tools/cmdstate.mjs` で段遷移を見るだけの監査では
気づけない。実機の保存ファイルで線の本数まで見て初めて発覚した
（`tools/functest.sh` の `cm_copy_scale_esc_chain_reclick_noop`：本物は
ESC 3 回で複写した 2 本が消えて 30 本に戻るのに、移植は 32 本のまま）。

**対策**：「ESC で段が一つ戻る」ことを確認しただけで「その段の取り消しが
効いている」と思わないこと。取り消しが呼ぶ関数（ここでは `place_undo`）が
**どの変数を見て**判断しているか（フラグ・カウントの控え）を確認し、
置く処理の**別の経路**（`place_by` を通らない独自の置き方）がその変数を
一度も触っていないなら、置いた側にも同じ控えを立てる処理を足すこと。

### 実機保存の全経路（ファイル保存メニューまで）は、座標がとても大きい複写で壊れることがある（tools/onlykind.py の固定ヘッダ解析）

③数値倍率 の倍率欄に `9000`（検査は通る値）を打って置いたあと
`tools/functest.sh` でファイル保存までやらせると、本物の `.JWC` が
`tools/onlykind.py`（`tools/linedump.py` 等が使う、ヘッダの件数から
データの開始位置を逆算する共通クラス）で
`cannot find where the data starts` という読み取り失敗になることがある
（`10000` でも `9000` でも再現、`20000`——③の検査で断られる値——では
再現しない＝検査を通って実際に大きな複写ができたときだけ起きる）。
原因は未診断のまま（実機側の保存そのものが変なのか、`onlykind.py` の
固定オフセット探索がこの大きさの pool_len で破綻するだけなのかを
切り分けていない）。`tools/steps_table.py`（画面の行を読むだけで保存は
しない）では同じ倍率が問題なく通ることを確認済みなので、入力検査の
境目そのものは実機で確認できている——**この罠は「大きな複写を保存まで
確認する」別の調査が必要という記録**で、③の検査ロジックの正しさとは
別の話。次に大きな倍率複写の保存を確認するときは、まずこれが
`onlykind.py` 側の限界か本物側の挙動かを切り分けること。

### 「取り消し」は控えた値を書き戻すとは限らない——同じ関数を引数を入れ替えてもう一度呼んでいることがある

移動 ⑥回転・③数値倍率・④ﾏｳｽ倍率 の ESC 取り消しを実装するとき、最初は
複写側の `place_snapshot`/`place_undo`（個数を控えて増えた分を削る）に
倣って「変形前の座標をまるごと控えて、ESC でそのまま書き戻す」
（`JwcLine`/`JwcArc`/`JwcText` の生の構造体をコピーする方式）を作った。
生成した図形は見た目にも数値にも正しく戻るが、192.168.11.37 の実機と
`tools/functest.sh` で生バイトまで突き合わせると、実機は控えた値そのもの
には戻っておらず、**最後の数ビットだけ違う値**になっていた
（`line5.x0` が変形前 `0x4223e460` のところ、実機の ESC 後は
`0x4223e45e`）。つまり本物は「変形前の値を覚えておいて書き戻す」のでは
なく、**同じ `turn_range`/`scale_range`（移植ではこの名前）を、基準点と
置く点を入れ替え・角度を逆（または倍率を逆数）にしてもう一度呼んで
計算し直している**——move_range の取り消しが `move_range(c, d, -dx, -dy)`
と「同じ関数を逆向きに呼ぶ」形になっているのと同じ流儀だった。

**対策**：複写・移動のような「位置を計算し直す」系の取り消しは、まず
「値を控えて書き戻す」を疑う前に、**同じ計算をする関数が既にあるなら、
引数を入れ替えて逆方向に呼ぶだけで済まないか**を実機の生バイトで試す
こと。見た目や丸めた小数点表示では両方とも「正しく戻った」ように見える
ので、画面や 3 桁表示の比較だけでは区別がつかない——`tools/functest.sh`
のような生バイト比較まで行って初めて「どちらの方式か」が分かる。

（余談：この方式でも実機とビット単位で一致しない座標が一点だけ残った
——基準点と置く点の y が同じ値になる置き方で、複数の線が共有する頂点の
1 座標だけ最後の 1 ビットが違う。他のあらゆる組み合わせ・他の変形の種類
ではビット一致したので、浮動小数点の丸めが非可逆な境界に乗っただけの
可能性が高いが、decomp 未確認のまま——nokori.md 参照。）


## 共通関数の中に追加した if は、その関数自身の `return 0` より前に置くこと（2026-10-07、attr7）

`cmd_top()`（`src/cmd.c`の呼び出し元の巨大な if 連鎖）に複写・移動 ⑦ の新しい段（段 26・27）
を扱う `if (JW_MOVING(c) && c->stage == 27) { ... }` を、既存の
`if (JW_MOVE_CMD(c->command)) { ... 最後に return 0; }` という、複写・移動共通の
ブロックの **後ろに兄弟として** 追加したら、`item==1` を押しても段が一切進まず
（`jw_cmd_top` が `cmd_top()==0` を受け取って `top_item` を記録するだけのパスに落ちる）
バグを踏んだ。原因は `JW_MOVE_CMD(c->command)` は呼ばれた瞬間に TRUE なので、そのブロックの
中のどの `if (c->stage == ...)` もマッチしなければ、ブロック自体の最後の
`return 0;` が無条件で実行され、関数の残り（自分が追加したブロックも含め）は
**一切評価されずに関数が戻ってしまう**。

症状は分かりにくい：`c->stage` は正しく進む（段4→段27）し、`top_item` も
記録されるので「何か起きている」ように見えるが、自分の新しいフラグ（`attr_group` 等）は
一切書き換わらず、`c->stage` もそのままで止まる。`tools/cmdstate.mjs`（実機不要、
port 内部状態）で `type 1` しても `stage=27` のまま、`attrg=0` のままだったことで
発見した。

**対策**：既存の `if (JW_MOVE_CMD(c->command)) { ... }` のような「このコマンド専用」ブロックが
最後に無条件の `return 0;` で閉じているなら、そのコマンドの新しい段は
**その `return 0;` より前に** 挿入すること。外側に追加してもビルドは通るし、
單体テスト（stage 遷移のみ）でも最初の一手（段へ入る持ち）は正しく見えるので、
段の中で項目を押すところまで確かめないと気づかない。

## 「欄をどの段から開いたか」を覚えていないと ESC/Enter の戻り先を間違える（2026-10-07、円線接）

円線接 ②接円（半径と２条件）の各小項目（①１線１円〜⑥２点）は、半径の欄
（`①接円半径`）を**最初の段からでも、一つ目を選んだあとの2番目の段からでも**
開ける作りになっていた（`src/cmd.c` の item ディスパッチが
`(c->stage == 40 || c->stage == 41) && item == 1` のように両方を受けていた）。
ところが欄を閉じる側（[ESC]・[Enter] とも）は「このコマンドの最初の段」を
決め打ちで戻していたので、2 番目の段（一つ目をすでに選んだあと）から欄を
開いて確定・取り消しすると、**その選んだ分が無かったことになって**最初から
選び直しになっていた（画面は普通に戻るので、選んだはずの線をもう一度選ぶまで
気づかない）。

**対策**：複数の段から同じ欄を開ける作りでは、開いた瞬間の段番号を専用の
控え（`c->tan_r_back`）に取っておき、閉じるときはそこへ戻す。固定の戻り先を
ハードコードしない。

## 同じ段番号を「初回」と「くり返し」の両方に使う場面は、段番号だけで ESC を判定できない（2026-10-07、円線接）

円線接 ①接線 ②円周点 は、円を指示する最初の訪問（まだ接線を 1 本も
引いていない）と、1 本引いたあとループで戻ってくる訪問の**両方が同じ段
番号（16）**を使う（③指定点は 2 と 4 で段番号を分けていたので気づきやすかったが、
②円周点 はそうなっていなかった）。段番号だけを見て ESC の着地先を決めると、
「まだ何も引いていないので ①接線 の行へ」なのか「もう引いたので全部取り消して
同じ段に留まる」なのか区別できない。`tan_start()` が控える `n0_lines`
（このコマンドに入った時点の線の本数）と `d->n_lines` を比べて、増えていれば
「引いたあとの訪問」と判定した。

**対策**：段番号が初回と継続で共用されている箇所を見つけたら、段番号以外の
状態（今回の操作で何かを作ったかどうかの控え）で分岐すること。

## 「もう片方のボタン」専用の脇道は、持ち物の有無ごとに別々に実装されがち（2026-10-07、＜ の線切断）

＜（command==7、コーナー連結）は「Ａ を選ぶ前の右押しは線切断」という脇道を持つが、
これを実装するとき `if (c->pick_a < 0 && right) { …線切断… }` のように**「まだ何も
選んでいない」ことまで一緒に条件へ入れてしまった**。実機で確かめると、右押しの
線切断は Ａ を選んだあと（【Ｂ】を待っている段）でも同じボタンで同じことが起きる
——`pick_a` の有無は無関係だった。`pick_a < 0` という条件は「Ａ を選ぶ前の画面
でしか測っていない」という**測定の範囲**をそのまま「仕様」として書き込んでしまった
もので、後段（Ｂ待ち）での右押しを一度も試さないまま「右押し＝線切断は最初の
押しでしか効かない」という誤った決め打ちになっていた。後段での右押しは
素通りして次の `if (c->pick_a < 0) { …Ａを選ぶ… }` にも当たらず、最後の
「Ｂ を選んでコーナー連結する」節まで落ちて、ボタンの左右を見ずに**誤って
コーナー連結**してしまっていた（`tools/functest.sh '90 160 left' '220 157 left'
'598 300 right'` で実機と座標がまるで違う結果になって気づいた）。

**対策**：「もう片方のボタン（especially 右押し）は特別な脇道」という仕組みを
見つけたら、その脇道を**「何も持っていない」状態だけでなく、持ち物がある他の
どの段でも**実機で試すこと。`a && b` の条件で脇道を切るとき、`a`（ボタン）と
`b`（進捗の状態）のどちらが本当の条件か——測った場面がたまたま両方 真 だった
だけではないか——を疑う。ここでは「切った線が、いま持っている Ａ 自身だったら
Ａ を外す」「Ａ より後ろの番号だったら `jwc_remove_line` の詰めに合わせて
添字を一つ減らす」という、持ち物の調整も合わせて要った（`src/cmd.c`、
`tools/cases/probe_corner_cut.txt`）。

## 内部フラグを解くと、升の表示が壊れて「無関係な ESC 節」が代わりに発火する（2026-10-08、□ box_angle_esc_unlock）

□ の `②角度` を確定する [Enter] は、`c->box_fix`（寸法を決めて置いている＝次の
1 押しで即座に置ける状態）を無条件で 0 にしていた。これは「回転を確定したら
2 点待ちの `box_mode` へ切り替える」という、寸法をまだ決めていないときの経路
（`box_fix` がそもそも 0）にだけ正しい話で、**既に `box_fix` が立っていた
（寸法確定→配置→②角度 の順）ときも同じように 0 にしてしまっていた**。

これの症状は段遷移を見ているだけでは気づけない：`c->stage` は動かず、
`box_rot`/`box_ang` も正しく更新される。壊れるのは**帯の見た目**（`src/ui.c:4084`
の `box_mode` 分岐は升＝`|①|②|③|④|` の入った文字列を持たない、ただの
`始点指示 (L)free (R)Read` 行）で、升が無い帯では `jw_ui_top_cell_x()` が
数字キーの升を見つけられず、digit キーでの再度の項目選択（`②角度` の
reopen）が**無反応**になる——エラーも出ず、ただ何も起きない。

さらにその先で、効かなかったはずの reopen のせいで `c->typing` が 0 のまま
だったので、次に押した [ESC] は「欄を閉じる」節（`c->typing` 前提）を飛ばして、
**順番がもっと前にある別の汎用 ESC 節**（`!c->pressed && !c->typing` かつ
`c->undo_lines` が立っているときに直前の実体を取り消す節）に先取りされ、
確定済みの箱をまるごと消してしまった。実機は reopen が効く（帯が升つきの
まま）ので、この汎用節には落ちず、箱は残る——**両者の差は「ESC が効かなく
なった」ではなく「ESC が別の節に奪われた」**というかたちで出る。

対策：ある状態フラグ（ここでは `box_fix`）を、画面の帯（升の有無）と
紐づけて見る側（`jw_ui_top_cell_x` 経由の digit キー、`src/ui.c` の帯選択）が
あるなら、そのフラグをサブ状態の確定（ここでは「角度を決めた」）だけを
理由に解除しない。解除してよいのは、実機の帯が実際に変わる（升が消える）
ときだけ——**実機の帯を `tools/steps_table.py` で段ごとに読み、升の並びが
変わらないなら、内部フラグも変えない**。`cmdstate.mjs` で `box_ask` や

## 自動生成の段テーブルは「測った場面」しか持たない——新しい入口（RR 等）の文言は手で足す（2026-10-08、┣ 線伸縮）

`src/stage.h` は「どの段でどの文字列が出たか」を実機の自動歩行（`tools/menus_table.py`/

hand」とある。ところが┣（線伸縮）の RR（同位置の二度目の右押しで「指定点へ」→「基準線へ」
に切り替わる帯）は、その自動歩行が一度も試さなかった入力（RR 自体が今回初めて見つかった
ジェスチャー）なので、**同じ段番号（stage 2）の行がテーブルに既にあるのに、中身は常に
「指定点へ」のまま**——自動キャプチャが別のモードの存在を知らずに記録したものだった。

この段番号を再利用しつつ別のモードの文言だけを出す場合、stage.h の既存行を書き換える
（自動生成を上書きする）のは筋が悪い（次に `tools/menus_table.py` を再実行すると消える、
かつ「測った場面」の記録として偽りになる）。代わりに `src/ui.c` の個別特別扱い節

`jw_ui_text` で上書き）に、新しいモードフラグ（`st_base_mode`）が立っているときだけ
発火する専用ブロックを足し、実機から直接採った生バイト列（`tools/probe.sh` の
出力そのもの）をハードコードした。

**対策**：自動生成テーブルの「同じ段番号なのに文言が違う」状況に出会ったら、まず
「その段番号が複数のモードで共有されているのに、自動キャプチャは 1 つのモードしか
通らなかった」可能性を疑う。生成物は書き換えず、個別特別扱いの層（ui.c の
`i == s->stage` ブロック群）に新しいモードフラグを足して上書きすること。

## 「もう一つの前端」を忘れると新しいフラグが片方でしか動かない（2026-10-08、┣ 線伸縮 st_base_mode）

## 「直前の値」ではなく「関数の入口」でゼロに戻るローカル変数（2026-10-08、文編集 ②方向）

文編集 ②移動・③複写 の ②方向（任意→Ｘ軸→Ｙ軸→XY軸、ovl15 3ab8:33ee の
`local_bc`）は **C のローカル変数**で、関数の入口（＝②移動・③複写へ新しく
入るたび）に無条件で 0 に戻る（`DS:[0x130]==2` のときだけ 3）。move先の点を
何度選んでも関数呼び出し自体は一度のままなので、同じセッション内で複数の
文字を続けて動かしても方向は保たれるが、[BS] で項目の行へ戻って ②移動 を
**選び直す**と、実機はかならず `任意` まで戻る。

port の `c->te_dir` は `JwCmd` 構造体のフィールドで、プログラム開始時に
一度ゼロ初期化されるだけ（`memset` は `jw_cmd_init` の 1 回だけ）——
「項目を選び直す」たびの初期化が無いと、C の一時変数が毎回ゼロから始まる
挙動を、構造体に居座る値で近似してしまい、2 回目以降だけ実機とずれる。
decomp のローカル変数が「呼ばれるたびゼロから」なのか「一度構えたら
持ち越す」のかは、関数の入口のコード(`local_bc = 0;` のような代入が
分岐の外・関数の先頭にあるか) で判定し、port 側でも「新しく入る」
遷移点（ここでは top_item が 0 から 2/3 になる 2 箇所：直接クリックと
帯/数字キー）全部に同じリセットを置くこと——1 箇所だけ直すと経路違いで
また抜ける。

## 同じオフセットを「往復」の全部の脚に足すと符号の和で消える（2026-10-08、文編集 ①書き換え の ずれ位置）

文字基準点 の「ずれ位置」（横位置・縦位置、mm）を `ed_place` へ渡す配線で、
最初は `jwc_edit_text_at`（ovl15 3ab8:08b3→2e67→7132→1f66 相当）が内部で
`ed_place` を 3 回呼ぶ構造（基点 P を求める 2 回・`s=-1`、P から新しい
始点を出す 1 回・`s=+1`）の**全部**に同じ offh/offv を `t += offh*s`
という形で足した。`s` の和は -1-1+1=-1 なので何か残るはずだと思い込んで
いたが、単体テスト（`jwc_edit_text_at` を直接呼ぶだけの小さな `.c`）で
確かめると、offh=10 でも結果の x0/x1 が offh=0 と**ビットまで同じ**だった
——3 回の呼び出しは r2/r3 が前の呼び出しの出力をそのまま次の入力にする
連鎖なので、各回に足した定数項が次の回の「原点」にすでに畳み込まれて
おり、単純な `s` の線形和では予測できない形で打ち消し合う。

`jwc_move_text`（`ed_place` を 1 回しか呼ばない）では同じ offh がそのまま
効くので、「結果が 0 ならロジックが呼ばれていない」と早合点しがちだが、
実際には呼ばれた上で数学的に消えていた。**対策**：複数回呼ぶ「往復」構造
に新しい加算項を足すときは、全部の呼び出しに機械的に同じ値を渡さず、まず
単体テスト（実機不要、`tools/cc.sh` で小さい `.c` を書いて呼ぶだけ）で
「足した値がちゃんと結果に出るか」を先に確認してから、足す場所を
1 箇所（ここでは最後の `s=+1` の 1 回だけ）に絞ること。

## 計算の中身が単体テストで合っても、それを呼ぶ「鍵」の前提が実機と食い違っていることがある（2026-10-08、文字基準点 の ③横位置・⑤縦位置）

`FUN_3ab8_0d67`（文字基準点 の盤）を decomp で読んで、①確定・②横回し・
④縦回し が数字キー 1/2/4 で動くことは別のセッションで実機確認済みだった
ので、「同じ帯にある③横位置・⑤縦位置も数字キー 3/5 で開く」と決め打ちで
実装し、計算（`ed_place` への offh/offv 配線）は単体テストで正しいと
確認してから 192.168.11.37 の実機に回した。ところが本物はこの手順
（`type 1|type 3|type 10|key enter|type 1`）では文字の位置が一切動かず、
port だけ動いた——**計算が単体テストで正しくても、それを起動する UI 側の
前提（この数字キーでこの欄が開く）は実機でしか確かめられない**。decomp を
読んで「項目はあるはず」までは確認できても、「どの鍵がその項目番号を
本当に送るか」は読み違えることがある（行に `|` 区切りの項目が 5 つ
あっても、全部が数字キーで選べるとは限らない——入力欄になっている項目は
マウスでその列を直接押す専用で、数字キーには反応しない、という可能性も
decomp だけでは除外できない）。**対策**：数字キー・マウス帯クリックの
どちらで項目に入るかは、仮に決め打ちで実装したとしても、**ロジックの
単体テストとは別に**、実機で同じキー列を踏んで検証するまで「decomp
照合済み」と書かないこと。

**2026-10-08 追記・前段の推測は外れだった**：上の「digit-key 前提そのもの
が実機と食い違っている」という結論は、`tools/probe.sh`（ローカルに built
済みの `../dosv_emu_cpp` で `orig/JW_CADV.EXE` を直接動かせる——192.168.11.37
を待たずに検証できる）で切り分け直すと**誤りだった**。`sh tools/probe.sh 28
400 140 t 1 t 3 t 10 e` は本物でもちゃんと行 1 を `ずれ位置 横 =` の欄＋
ものさしに変え、打った `1`・`0` も画面に出る——**トリガー（command==28・
top_item==1・te_sub==1 で数字キー 3/5 が③/⑤の欄を開く）は実機どおり正しかった**。
食い違っていたのは「欄が開くか」ではなく「開いた欄に打った値が、文編集
①書き換えの確定で実際に座標へ反映されるか」——`SAVE=1` で保存結果を見ると、
値を打って確定しても本物の文字の座標は 1 ビットも動かない。**教訓**：
「digit キーで値を打てたのに実機で動きが見えない」という測定結果だけから
「トリガーが違う」と決めつけない——**まず欄が本当に開くかどうかを単独で
確かめる**（画面の文字列が変わるかだけ見れば済む、`tools/probe.sh` の
`--- what it wrote` で十分）。欄は開くが確定後の座標に効かない、という
「途中までは実機どおりだが、使われ方の末端だけ違う」という形の不一致も
あり得る。直し方は src/cmd.c の `jwc_edit_text_at` 呼び出し（①書き換えの
確定）に offh/offv の代わりに `0.0f, 0.0f` を渡すだけで済んだ——欄・鍵処理・
値の記憶はそのまま、使うところだけ外した。

### 「command==28 専用」のつもりで `c->top_item` だけを見ていた節に、別の命令を同じ数字鍵の道へ通すと誤爆する（文字 band2 ①基点変）

`jw_cmd_te_digit`（文編集専用のつもりで書かれた、数字鍵の処理）の中に
`if (c->top_item == 6 && c->te_pick < 0) { ... }`（文編集 ⑥文字種類変更）
という、`c->command` を見ない節があった。`top_item==6` は command==28 でしか
出ない値のはずだったので、これで安全だと思われていた。ところが
文字（command==13）band2 の①基点変（文字基準点の盤）を直すために
main_wasm.c の数字鍵の呼び出し先を `jw_cmd_te_digit` へ command==13 にも
広げたところ、文字 band1 の⑥縦字を押したときの副作用（`top_item=6` に

`c->command==` の有無で確認し、無いものには明示的に足すこと
（修正は `c->top_item == 6` を `c->command == 28 && c->top_item == 6` に
