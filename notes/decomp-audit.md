## ★ 家の Claude へ：最初にやること（2026-10-05 夜の引き継ぎ）

**まず「デコンパイルとの一致の洗い出し」から始める。画面の差を直すのはそれから。**

背景：この移植の UI 層（入力欄、[ESC]、行や札の出し入れ）は、最初から画面を測って合わせる作り方で、
decomp を読んでいない。測っていない組み合わせが本物とずれる。ユーザーに「創作だらけ」と指摘された。
今日、決まった一部を decomp と照合して直したが、まだ大部分が未照合。

### 洗い出しの手順
1. 命令ごとに、decomp（decomp/ovl*/all.c、tmp/dis/ovlNN.dis、`python tools/altlift.py --ovl N 開始 長さ`、
   `python tools/strref.py "文字列"`）から本体を読み、**仕様（状態変数・押し／[ESC]／[BS]／数字キーの遷移）**を起こす。
   Ghidra C は x87 エミュレータ呼び出しで崩れていることが多い。dis と DS 画像（DGROUP）を直接読む。
2. 移植の実装と突き合わせ、**一致／不一致／未確認**の表を作る（下の「照合済み」にならう）。
3. 不一致は decomp どおりに直す。決まらないものは測定を根拠にしてよいが「測定のみ・decomp 未確認」と書く。
4. 実装後は**テストより先に decomp との一致を確認**し、そのあとテスト。
並列にサブエージェントへ読ませるのが速い（今日は 5 つ並列で 10〜20 分で返ってきた）。**サブエージェントの
結果は鵜呑みにせず、番地を確認する**（報告には推定が混ざる）。

### 10-d. 寸法（今夜 着手。10-c の param_1 の謎を解いただけ・コード変更なし）

項目 10 のうち **寸法**（command==14）だけを担当。10-c が残した宿題

**手順**：`tools/callsites.py` は link アドレスを引数に取る
（`2ab8:off` の形。`OVL_SEG=0x2ab8` は `tools/overlays.py`）。
`decomp/entries/27.txt` に `740f` という行があり、これが
`FUN_4000_1f8f` のゴースト地（RESUME 既出：`4000:1f8f` のギアドラ
表記 + 0x5480 = `3ab8:740f`、つまりリンク時 `2ab8:740f`）と一致する
ので、そのまま `python tools/callsites.py 2ab8:740f` に通した：

```
3 call sites for 2ab8:740f (linear 031f8f)
  root    000a2e  overlay 27  pushed: ?
  ovl11   002c12  overlay 27  pushed: 0x0001
  ovl12   001f00  overlay 27  pushed: ?
```

- **`ovl11 002c12`（push 定数 1）**：10-c が既に特定していた「変形の
  メインディスパッチャ」(`FUN_3ab8_305f`、ovl11)。`python tools/disasm.py
  --ovl 11 ...` で `2c12` 近辺を読むところまではしていないが、10-c の
  記述（②包絡処理変形＝`3ab8:325e`）の中からの呼び出しであることは
  push 定数 1 と ovl11 という組み合わせだけで十分（他に ovl11 から
  ovl27:740f を呼ぶ場所は無い）。10-c が引用した port 側コメント
  （cmd.c:10548「変形 ②包絡処理変形 の **範囲内消去**（終点を右ボタン
  で押したとき）」）が、まさにこの `param_1==1` の呼び出しに対応する
  ——**「範囲内消去と同じ関数を使っている」という既存の測定ベースの
  実装は、この 1 点では decomp と矛盾しない**（式はまだ未確認）。

  コマンドディスパッチャ**（`jmp word ptr cs:[bx+0x1f5c]`、
  `bx = (command_number-1)*2`。表の中身は
  `python3 -c "..."` で `tools/overlays.py` の `chain()` を使って
  `0x1f5c` から 32 個の word を直接読んだ）。表の 25 番目のエントリ

  ```
  02c9fd  mov byte ptr [0xc13e], 1
  02c9ff  sub ax, ax
  02ca00  push ax                 ; param_1 = 0 の "push" が
                                  ;   `mov ax,imm16`ではなく
                                  ;   `sub ax,ax`なので callsites.py が
                                  ;   定数と認識できず "?" になった
  02ca01  int 3fh  OVERLAY 27 -> 2ab8:740f
  ```

  ——`FUN_4000_1f8f` の冒頭 `if (param_1==1) goto LAB_3ab8_7452;`

  `sub ax,ax; push ax; int 3fh OVERLAY27->740f` だった。表の全エントリ
  までは突き合わせていないが、push 0 という値は `ovl12` 側のコマンド
  25 の枠と同じなので、**消去がもう一箇所から（別のキー・別の再入口
  から）同じ呼び方で入れる二つ目の入口**と見てよい（寸法とは無関係）。

**`0x2cbad`（ovl-off `0x202c`）はディスパッチャそのもの**：`push bp` のあと最初の分岐
`cmp word ptr [bp+6], 1` が呼び出し側の `push ax(item); push cs; call 0x2cbad` の `ax`（=item 1/2/3）
を見ている（near call の戻り番地 2 バイト + 呼び出し側が積んだ `cs` 2 バイト + `ax` 2 バイトで
ちょうど `bp+6`。`push bp` が無い版に見えたのは最初の altlift ダンプが retf の直後から始まって
いて見落としていただけで、`--raw` で確認したら `02cbad: push bp` はちゃんとあった）。
item==1 なら `0x2cbe4`（①２点からの距離、前回確認済みの帯のまま）。item!=1 なら `0x2d387` へ、
そこで `cmp [bp+6],2` → item==2 なら `0x2d390`（②正多角形）、item!=2 なら `0x2e667`（③座標値、
未読）。

**②正多角形の stage1 は「任意寸法／寸法指定」の二択が最初に立つ**ことが分かった。前回の
write-up は「①任意寸法の正多角形」を唯一の経路のように読んでいたが、実際には帯文字列

```
0x526e '正多角形'　0x5277 '中心から'　0x5280 'の距離指定'
0x528b '|任意寸法の%s |寸法指定の%s |'
```

（いずれも root DGROUP、`base = hdr + 0x33750` からの直接オフセットで、`mov ax, 0x526e` の
ような即値がそのままこの base への足し算になっている——円線接などで使ってきた `strref.py` の
大きい相対値 `0x3fxxx` とは別口の、同じ base を使う「小さい即値」経路）
を組み合わせて **`|任意寸法の◯◯ |寸法指定の◯◯ |`** の帯を出し、`0x1bb4:0x2cb4`
（stage0 でも使っていた「項目選択」関数）で 1 か 2 かを選ばせる（`0x2d3c0`〜`0x2d42e`、範囲外は
`0x2d3c0` へリトライ）。選択結果は `[bp-0x122]` に残る。

- **選択 1（任意寸法）**：`[bp-0x122]!=2` なので即 `0x2d49e` へ飛ぶ。これは **既存 port の
  実装（src/cmd.c:5511〜、コメント「①任意寸法の正多角形」）とそのまま一致**——port が今まで
  実装していたのはこの枝だけで、取り違えは無かった。
- **選択 2（寸法指定）**：`0x2d435` で第二の帯を組む：

  ```
  0x52a9 '|%s一辺%s |%s頂点%s |一辺の長さ指定 |'
  ```

  これが前回見つけていた「一辺／頂点／一辺の長さ指定」の 3 択そのもの（`0x1bb4:0x2cb4` を
  範囲 1..3 で呼び直す、`0x2d42e`〜`0x2d49e` がリトライループ）。**つまりこの 3 択は
  「寸法指定」を選んだときだけ出る、②正多角形のネストされたサブメニューであって、
  独立項目ではない**——前回の write-up は「３通りの入力方式の選択」が stage1 のどこに
  刺さるか確定していなかったが、ここで確定した。選択後も **同じ `0x2d49e` に合流する**
  （任意寸法の枝と寸法指定の枝は `0x2d49e` 以降で再び同じコードを通る）。

**`0x2d49e` は「角数入力」の既定値つき帯を組む共通コード**だと分かった：

```
0x52cf '%sの角数 =               %s[%d]'
```

を `DS:[0x53f6]` の値を `%d` に詰めて表示し（`0x2d4b4 push word ptr [0x53f6]`）、
`0xad:0x16d4`（port の既存コードが「辺数入力」として使っている同じ数値入力関数――
cmd.c の `c->typing`/`c->typed` 経路に対応すると見られる、測定のみ・decomp未確認：
この対応は disasm からの読みで、実機キー入力との突き合わせはしていない）で読む。
入力が確定しなかった（`ax==-1`）ときは `[bp-0x122]` の値によって `0x2d3c0`（任意寸法の
選び直し）か `0x2d42e`（寸法指定側の選び直し）へ戻る——**「任意寸法」と「寸法指定」は
別物の最終処理ではなく、同じ角数入力に合流したあとに ESC で元の二択まで戻れる**という
構造。角数が決まったあと `0x2d519`〜 で `DS:[0xa118]`/`DS:[0xa11c]` と比較しクランプする
形跡があり（`22b2:7191` という比較ヘルパ）、続けて不正なら `0x53f6` に既定値を書き戻す
処理（`0x2d568`〜`0x2d576`）がある。**`DS:[0x53f6]` が「角数の既定値を次回のために覚える」
グローバルである、という前回の推測（「DS global、probably」）はここで decomp 上に確認が取れた**
（ただし `0xa118`/`0xa11c` に実際どんな数値―最小/最大の角数 3 と無制限など―が入っているかは
バイト列からは読めなかった。これも測定のみ・decomp未確認の域）。

**「寸法指定」を選んだ場合に続くはずの 頂点／辺中（中心点基準）・内接⇄外接 の切替は、
この `0x2d49e` 直後にはまだ現れていない**。角数入力が確定したあと（`0x2d54c` 以降、
`[bp-0x24]==0 or 0x66` で分岐するあたり）から先は未読——前回の write-up が見つけていた
`'◇ 頂点 辺中 %s%s |①%s%s|'`・`'● 中心点 %s%s |①角数%s|'`・`'内接 '` の各帯は、
別の strref.py 走査（大きい相対値 `0x3fxxx` 系、今回の `0x52xx` 系とは別のテーブル）から
見つかったもので、**この `0x2d49e` 以降のどのアドレスで実際に使われるかはまだ突き合わせて
いない**。`0x5300`='● 中心点 %s%s |①角数%s|' は今回読んだ範囲のすぐ先（`0x2d780` 付近）に
実際に出てくることを確認したので、その周辺（port の既存「中心点を押す→角数を聞く」処理の
decomp 対応箇所）に 頂点／辺中・内接／外接 の分岐が隣接しているはず——**次に進むならここ
（file-linear `0x2d780`〜、`python tools/disasm.py --ovl 22 0x2bff 0x200 --raw`）から**。

**今回は実装していない**：上記のとおり「寸法指定」の枝は 一辺／頂点／一辺の長さ指定・
頂点／辺中・内接／外接・実際の辺頂点計算のどれも disasm 上でまだ式まで追えておらず、
`polygon()`（src/cmd.c:8486、頂点基準・外接・単純な辺数入力の固定式）を書き換えるだけの
根拠が無い。「任意寸法」の既存実装（port の唯一の経路）は decomp と矛盾しないことが
あらためて確認できた（変更不要）ので、コードは変更していない。

#### 10-e 追補その2（2026-10-06 深夜、`python tools/disasm.py --ovl 22 0x2bff 0x200 --raw` から続けて `0x2d79a`〜`0x2e142` 付近まで読み進めた。write-up のみ・コード変更なし）

**訂正：「内接／外接」は多角形②正多角形の話ではなかった。** 前回 write-up が挙げていた
`'内接 '` という文字列は `base=hdr+0x33750` からの検索で見つけただけで、どの overlay の
コードが実際にそれを読んでいるかは未確認のまま「多角形のすぐ近くにある」と推測していた。
今回 `mov ax, 0x5cd8`（'内接' の DS オフセット）のバイト列 `b8 d8 5c` を exe 全体から
検索したところヒットは `file 0x1131a2` の 1 か所だけで、overlay チェーンで突き合わせると
**ovl26（線変更・複線化の overlay）の局所 `0x4da2`**——多角形（ovl22）とは全くの別物
だった。さらに `'外接'` という文字列は `JW_CADV.unp.exe` 全体を検索しても **1 件も存在しない**
（`b.find('外接'.encode('cp932'))` が終始 `-1`）。つまり「正多角形に内接／外接の切替がある」
という前回の仮説は、**10-b〜10-e で繰り返し踏んできた「字句近さの推測」と同じ罠**で、
根拠が無かった。この行は誤りとして撤回する。

**寸法指定の構造が全体像として確定した。** `0x2d49e`（角数入力、前回確定済み）のあと
`0x2d57e` で `cmp [bp-0x122], 2 ; je 0x2d588 ; jmp 0x2d79a`
（`[bp-0x122]` は stage1 選択＝1:任意寸法／2:寸法指定、前回確定済み）：

- **`[bp-0x122]==1`（任意寸法）は `0x2d79a` へ直行**。
- **`[bp-0x122]==2`（寸法指定）は `0x2d588` へ**（文字列 `0x52ef`
  `'底辺の%s  |①%s|'` を組み、`0x1bb4:0x2cb4` で 2 択——値 `1` なら
  `int 0x3f`（別 overlay 呼び出し、未読）で既存の線を拾う系、それ以外（`0x2d697`、未読）
  は数値を直接打つ系と見られる、**測定のみ・decomp未確認**）。

**`0x2d79a`（ovl-off `0x2c19`）は「点を一つ拾う」共通ループで、任意寸法・寸法指定の
両方から呼ばれる。** 最初の 1 回目は中心点を拾い（確定すると `0x2d878` で
`[0xb37e]`/`[0xb380]` という DS グローバルに中心座標を保存する——これが円の中心点の
置き場所と見られる、測定のみ・decomp未確認）、`0x2d8b7` で
`cmp [bp-0x122], 1 ; je 0x2d8c1（任意寸法） ; jmp 0x2db10（寸法指定）` と分かれる：

- **任意寸法（`0x2d8c1`→）**：`0xa128` テーブルと `DS:[0x53f6]`（角数、前回確定済み）を
  読み直したあと `0x2d922` に合流し、**同じ `0x2d79a` ループをもう一度回して「二点目」
  （半径・向きを決める点）を拾う**。つまり port の既存 `polygon()`（中心点＋二点目の
  マウス押しで半径と向きを決める）と構造として一致する。
- **寸法指定（`0x2db10`→、ovl-off `0x2f8f`）**：二点目をマウスで拾う代わりに、
  `0x2db42`〜`0x2dc20`（ovl-off `0x2f99`〜）で **「一辺／頂点／一辺の長さ指定」の
  どれを選んだか**（`[bp-0x120]`、前回 `0x2d435` 付近で確定済みの 1/2/3 セレクタと同じ
  変数）に応じてラベルを組み替えた数値入力の帯を作り（`'中心から' 0x5337`・`'一辺' 0x5347`・
  `'頂点' 0x534c`・`'までの距離' 0x5351`・`'一辺の長さ' 0x535c`・`'[ESC] ' 0x5337`・`' = ' 0x5373`・
  `'[%10.2f]' 0x5377`、いずれも root DGROUP `base+0x52xx` 帯）、`0xad:0x16d4`
  （port の辺数入力と同じ数値入力関数、測定のみ・decomp未確認）で**数値（マウスではなく
  キー入力の長さ）**を読む。つまり「寸法指定」は二点目を押す代わりに長さを打ち込む経路で、
  **port には現状この枝が丸ごと無い**。

**頂点／辺中（`DS:[0x53f4]`）は「二点目を拾う」ループ自体の一部で、任意寸法にもかかる。**
`0x2d922`（二点目ループの再表示入口）の直後 `0x2d927`〜`0x2d976`
（`'◇ ' 0x531a`＋`[0x53f4]==0 なら '頂点' 0x531e／!=0 なら '辺中' 0x5323`＋
`' %s%s' 0x5328`＋`'|①%s%s|' 0x532e` で `'◇ 頂点 辺中 %s%s |①%s%s|'` の帯を再現）が
このループの毎回の再表示で `DS:[0x53f4]` の値を読んで '頂点'/'辺中' を出し分けている
（前回の write-up が見つけていた `'◇ 頂点 辺中 …'` の帯はここで実際に使われると確認）。
`DS:[0x53f4]` への書き込みは exe 全体でただ 1 箇所、file-linear `0x2da19`〜`0x2da23`
（ovl-off `0x2e98`〜`0x2ea2`）：

```
mov ax, 1
sub ax, word ptr [0x53f4]
mov word ptr [0x53f4], ax
jmp 0x2d922            ; 再表示
```

（＝ 0⇔1 のトグル）で、その直前のガード（`0x2d9ff`〜`0x2da17`、ovl-off `0x2e7e`〜）は
二通りの入り方を許している：
- `cmp [bp-0x24], 0x31 ; je 0x2da19` —— `[bp-0x24]` は `0xad:0x16d4`
  （数値入力、`0x2dc18` で呼ばれ `0x2dc20` で `[bp-0x24]` に結果が入る）が返す
  キー分類値で、`0x31` は ASCII `'1'`。**キー `1` を押すとトグルする**、と読める
  （測定のみ・decomp未確認：実機キー入力との突き合わせはしていない）。
- その手前の `[bp-0x64]!=0` かつ `[bp-0x22] < DS:[0xa5e]` かつ `[bp-0x1c] > 0x1b8`
  の三条件（画面座標らしい比較）でも同じ `0x2da19` に落ちる——**帯の「◇頂点 辺中」の
  文字そのものを画面上でクリックしてもトグルする**、という形に読める（これも測定のみ・
  decomp未確認）。

**`DS:[0x53f4]` は実際に頂点座標の計算を分岐させている**——寸法指定側の辺頂点計算ループ
（`0x2de8a`〜、`DS:[0x53f6]` 回ループして `bp-0x7e` を辺番号として回す）の中、
`0x2ddbf`（ovl-off `0x323e`）と `0x2e099`（ovl-off `0x3518`）の 2 か所で
`cmp [0x53f4], 1 ; je ...（辺中側の処理）` という分岐があり、`[0x53f4]==1`（辺中）と
`==0`（頂点）とで別のコード列（`0x22b2:0x6cc6`/`0x7258`/`0x7124`/`0x6e4b`/`0x6d14`/`0x7154`/
`0x6e99`/`0x75fe` など、固定小数点らしい演算ライブラリの別々の呼び先）を通る。
**ただしこのライブラリ呼び出し（`lcall 0x22b2, 0xXXXX` という形がこの関数だけで約20種類
出てくる——`0x2854`（帯への文字列コピー）以外は番号に名前が付いておらず、加減乗除・
平方根・sin/cos/atan2 のどれに当たるか disasm からは読めない）の中身までは今回も
手が届かなかった**。「頂点基準なら押した点がそのまま頂点、辺中基準なら押した点（または
打った長さ）は辺の中点で半径は `1/cos(π/N)` 倍……」という読みは幾何として自然だが、
**decomp の式としては未確認の推測にすぎないので、そのまま実装はしない**（指示どおり
「ambiguous なら guess で実装しない」）。

**結論（今回分）**：
1. 「内接／外接」という第二の切替は存在しない（上記の撤回）。実在するのは
   **頂点／辺中（`DS:[0x53f4]`、0=頂点/1=辺中、キー`1`または帯クリックでトグル）**の
   一つだけで、これは「寸法指定」固有ではなく **任意寸法（port が既に実装している経路）
   にもかかる**。つまり `polygon()`（src/cmd.c:8486）は「頂点基準」決め打ちの時点で、
   任意寸法の中だけで見ても **辺中基準を実装していない**という欠落がある
   （内接/外接ではなく、頂点/辺中の欠落として記録を訂正）。
2. 「寸法指定」は二点目のマウス押しの代わりに **一辺／頂点／一辺の長さ指定（`[bp-0x120]`、
   前回確定）で組み替えたラベルの数値入力**に分岐する別経路で、port にはこの枝が丸ごと無い。
3. どちらも最終的な頂点配置の式（辺中基準でどう半径・角度をずらすか、寸法指定の
   3方式がそれぞれどう数値から辺頂点を作るか）は `0x22b2` 番地の固定小数点演算
   ライブラリの約20種の呼び先を意味付けしないと読めず、**今回の持ち時間では届かなかった**。

**今回も実装していない**（式が decomp 上で確認できていないため）。**次に進むなら**：
`0x22b2:0xXXXX`（`0x6cc6`/`0x6d14`/`0x6e4b`/`0x6e63`/`0x6e99`/`0x6eb1`/`0x6f61`/`0x701d`/
`0x704d`/`0x7095`/`0x710c`/`0x7124`/`0x7154`/`0x718c`/`0x7191`/`0x75ec`/`0x75fe`/`0x7592`/
`0x7658`/`0x6d9b`）の呼び先をどれか一つでも特定する（`tools/disasm.py` でこのセグメントの
コードを直接読む、または dosv_emu_cpp の `DOSEMU_BP` でこの関数を単独で回し、
頂点/辺中・寸法指定それぞれでレジスタ/スタックの値がどう変わるかを実測する）のが
一番効率が良いはず。それが済めば `0x2ddbf`/`0x2e099` の分岐の中身（辺中の式）と、
`0x2db42` 以降の 3 方式（一辺／頂点／一辺の長さ指定）がそれぞれどう辺頂点を作るかの
両方が一気に埋まる。

#### 10-e 追補その3（2026-10-06 深夜、`0x22b2` の約20種の呼び先を全部特定した。write-up のみ・コード変更なし）

**約20種のうち静的解析だけで全部特定できた**（dosv_emu_cpp の `DOSEMU_BP` を使うまでも
なかった）。決め手は `tools/altlift.py` 自身が持っていた表（LOAD/STORE/MEMOP/STKOP/UNARY、
16 種）で、残りの 4 種 `0x7258`／`0x75ec`／`0x75fe`／`0x7658` だけが altlift でも `?` 付き・
未解決だった。この 4 つを `python tools/disasm.py 22b2:75fe 0x10`（＝ root 画像内の file-linear
`hdr + 0x22b2*16 + 0x75fe` を直読み）のように個別に逆アセンブルすると、**Microsoft C
ランタイムの数学エラーテーブル（`matherr` 用の関数名文字列つきディスパッチ列）の
エントリそのもの**だった：

```
root file-linear 0x2a0b2〜0x2a189 に 12 エントリ（各 9 バイト、1 関数につき 2 エントリ）：
  mov bx, <DGROUP 内の関数名文字列アドレス> ; mov dx, <同名関数の実装アドレス> ; jmp <汎用エラーハンドラ>
```

DGROUP（`base=hdr+0x33750`）から文字列を引くと `0x8e4b 'sqrt'`／`0x8e51 'pow'`／
`0x8e56 'log'`／`0x8e5b 'log10'`／`0x8e62 'exp'`／`0x8e67 'sin'`／`0x8e6c 'cos'`／
`0x8e71 'tan'`／`0x8e77 'asin'`／`0x8e7d 'acos'`／`0x8e83 'atan'`／`0x8e89 'atan2'`
の 12 関数ぶんがこの順に並んでいた（`pow,log,log10,exp,sin,cos,tan,asin,acos,atan,atan2`
の後に `sqrt` が手前にもう 1 組ある、計 12）。**そして `22b2:75fe` の file-linear
アドレス（`hdr+0x22b20+0x75fe = 0x2a11e`）が、この表の `'cos'` エントリ
（`mov bx,0x8e6c ; mov dx,0x6ac5 ; jmp 0x29f78`）の先頭と完全に一致**した。
同様に `22b2:75ec`（`0x2a10c`）が `'sin'` エントリ（`dx=0x6ade`）、
`22b2:7658`（`0x2a178`）が `'atan2'` エントリ（`dx=0x6c37`）の先頭とそれぞれ完全に一致した。
つまりこの 3 つは **「推測」ではなく「file-linear アドレスの数値一致」で確定**：

- **`22b2:0x75fe` = `cos`**（引数は 8 バイト double 1 個、`lcall` 前に
  `sub sp,8`→値を書く→呼ぶ→`add sp,8` という定形で渡し、戻り値は `ax` が指すポインタ先の
  8 バイト double、という従来の BX-operand 方式とは別の、もっと普通の C 呼び出し規約）
- **`22b2:0x75ec` = `sin`**（同上、引数 1 個）
- **`22b2:0x7658` = `atan2`**（引数 2 個＝16 バイト、`add sp,0x10` で確認。
  呼び出し順は `0x2dd62`〜`0x2dd92`：先に `[bp-0x132]`(=dx) を push、次に `[bp-0x144]`(=dy) を
  push、cdecl の「あとに push した方が先頭引数」規則で `atan2(dy, dx)` と読める——
  `[bp-0x144]` は `0x2dcb2` で `pickedY - cy` として作られ、`[bp-0x132]` は `0x2dce2` で
  `pickedX - cx` として作られているので、標準の `atan2(y,x)` そのもの）

既知の 16 種（LOAD/STORE/MEMOP/STKOP/UNARY、`tools/altlift.py` の表どおり）と合わせて、
RESUME に挙げていた約20種の呼び先は**これで全部特定済み**：
`6cc6`=LOAD f32／`6d14`=LOAD f64／`6d9b`=LOAD i16／`6e4b`=STORE f32(keep)／
`6e63`=STORE f32(pop)／`6e99`=STORE f64(keep)／`6eb1`=STORE f64 引数(pop)／
`6f61`=ftol／`701d`=`-`／`704d`=`*`／`7095`=`+`／`710c`=`*`／`7124`=`/`／`7154`=`+`／
`718c`=`+`(pop2,push1)／`7191`=compare／`7258`=型変換のみ（数値は変わらない no-op、
altlift の表どおり）／`7592`=sqrt／**`75ec`=sin（新規確定）**／**`75fe`=cos（新規確定）**／
**`7658`=atan2（新規確定）**。

**この特定だけで `0x2ddbf`／`0x2e099` の辺中側の式が decomp 上で追えるようになった：**

`0x2ddc9`〜`0x2de67`（頂点／辺中の分岐のうち `[0x53f4]==1` 側、X 座標）を読むと

```
[bp-0x42] = [bp-0x42](元の値 R) / [bp-0x112]      ; 0x2ddc9〜0x2dddf
[bp-0x6c] = [bp-0x86] + [bp-0x6c]                  ; 0x2ddec〜0x2ddff（角度を 1 歩進める）
radiusScale = [bp-0x42] （上の R/[bp-0x112]、型変換だけの 0x7258 を挟む）
[bp-0x5e](X) = radiusScale * cos([bp-0x6c]) + [bp-0x12e]   ; 0x2de04〜0x2de29
[bp-0x7c](Y) = radiusScale * sin([bp-0x6c]) + [bp-0x140]   ; 0x2de2e〜0x2de63
```

（`[bp-0x12e]`／`[bp-0x140]` は中心座標 cx/cy、`0x2de21`／`0x2de57` でそれぞれ最後に
足されている——`polygon()` の `c->x0`／`c->y0` に対応すると見られる、位置の対応は
確認済みだが変数名そのものは cmd.c 側に合わせて読んだだけ）。

**`[bp-0x112]` の中身も今回たどれた**（`0x2d8c1`〜`0x2d922`、`[bp-0x122]==1`＝任意寸法の
入口直後、ブランチ非依存の共通初期化）：

```
DS:0xa128 (f64) = 6.283185307179586 = 2π   ← 実際にバイト列を読んで確認（推測ではない）
DS:0xa0e0 (f64) = 0.5                       ← 同上
DS:0x53f6 = 角数 N（前回確定済み）

ST0 = 2π / N                 ; 0x2d8c1〜0x2d8d3（= step、1 頂点ぶんの full 中心角）
[bp-0x56] = step             ; 0x2d8d8（keep）
ST0 = step * 0.5 = π/N       ; 0x2d8e0（710c=`*`、この乗数が 0.5 だったと今回バイト列で確認）
[bp-0x19c] = π/N             ; 0x2d8e9（keep）
[bp-0x86] = π/N               ; 0x2d8f2（STORE、pop）
[bp-0x112] = cos(π/N)         ; 0x2d8fb〜0x2d916（[bp-0x19c] を再ロードして cos へ渡す）
```

つまり **`[bp-0x112] = cos(π/N)`（半頂角のコサイン）で確定**——幾何として
「辺中（apothem）で押した距離 a から外接円半径 R を作るなら R=a/cos(π/N)」という
自然な式とも一致する。**この部分（半径の補正式）は decomp のバイト列・定数まで含めて
確定とみてよい。**

**ただし `[bp-0x86]` が `π/N`（半歩）である点と、ループの実際の歩進構造は未解決のまま
残った。** `0x2ddbf`（最初の頂点）とは別に、同じ関数内にもう 1 か所ほぼ同一の
辺中コード列（`0x2e099`〜`0x2e141`、`[bp-0x112]`／`[bp-0x86]` を再利用）があり、
さらに `0x2de8a`〜`0x2dfc9`（`[0x53f4]` を見ない、無条件に `[bp-0x56]`(=π/N) を
`[bp-0x6c]` に足して次の点を作り、`[0x53f6]`(=N) と `[bp-0x7e]` を比べて辺を 1 本描く
ループ）がある。この 3 つがどう呼ばれる順番でつながり、「頂点」と「辺中プレビュー」の
どちらに半歩・どちらにもう半歩を割り当てるか（＝辺中トグル時に頂点が
`a0 ± π/N, ±3π/N, …` のどの符号・どのオフセットから始まるか）は、**今回も
最後まで追い切れなかった**。ここを external から測定で詰めるなら、
`DOSEMU_BP=+22b2:75fe DOSEMU_BPDBL=2` （8 バイト引数を double として読む）で
②正多角形→②寸法指定 or 任意寸法→頂点/辺中トグルを押しながら cos 呼び出しのたびの
引数（theta）を全部ログに取り、既知の center・クリック点・N から期待される
`a0 ± k*(π/N)` の数列と突き合わせるのが最短。

**結論（今回分）**：
1. `0x22b2` の約20種の呼び先は**全部静的に特定できた**（新規 3 つ：`75ec`=sin／
   `75fe`=cos／`7658`=atan2、file-linear アドレスが MSC ランタイムの matherr 名前表と
   数値一致で確定——推測ではない）。
2. 辺中（`DS:[0x53f4]==1`）の半径補正式 **`R' = R(クリック距離) / cos(π/N)`** を
   decomp のバイト列・定数（`0xa128`=2π、`0xa0e0`=0.5）まで含めて確定できた。
   中心・基準角 `a0=atan2(dy,dx)` は頂点基準と共通（`polygon()` の既存実装と同じ式）。
3. **ループの歩進（頂点ごとに π/N を何回・どちらの符号で足すか）は未確定のまま**
   ——ここが分からないと「辺中」トグルを `polygon()` に実装しても頂点の位相
   （どこから描き始めるか）を外す恐れがあるため、**今回も cmd.c の実装はしていない**
   （式の一部は確定したが、位相が確定していない以上 guess で埋めない、という
   プロジェクトの原則どおり）。「寸法指定」の 3 方式（一辺／頂点／一辺の長さ指定）の
   個別の数値→頂点変換もこのループの歩進が分からないと読めないため、今回も未着手。

**次に進むなら**：上の `DOSEMU_BP=+22b2:75fe DOSEMU_BPDBL=2`（cos）と
`+22b2:75ec DOSEMU_BPDBL=2`（sin）を同時に張って、頂点/辺中トグルを押した状態で
多角形の②寸法指定・任意寸法それぞれを実機で 1 回ずつ確定させ、引数列（theta の実際の値）
を記録すれば、頂点の位相はほぼ一意に決まるはず。式自体（cos/sin/atan2 への置き換え、
半径補正の分母）はこの write-up の式を使ってよい。

* `(2,2)`：Ａ・Ｂ とも点 —— 垂直二等分線（既存の測定 `center_pts` の

最初の押しが **右なら以後ずっと「二点」モード**（`c->cl_pts` 経路）、

`pick_line`）に固定してしまい、一度モードが決まると最後まで変わらない
——つまり「Ａを線で拾い、Ｂを点で拾う」という decomp にある 3 番目の

`(2,2)` ケースの実測であって、これ自体は decomp の `(2,2)` 分岐と矛盾

では正しい結果を出している）。ただし `(1,2)`/`(2,1)` の式（`FUN_1def_043a`・

今回読み切れておらず、**ここに手を入れると決め打ちになるので直していない**

無い」という事実まで。

decomp 側で見る限り「Ａ読み取りループ ⊃ Ｂ読み取りループ ⊃ 新しい区間の

いない。

**結論**：中心線は、decomp 側で「Ａ・Ｂの型（線／点）は押しごとに自動で
決まり、理論上は混在できる」という構造を新たに確認した。port は型を

**port の `c->ch_side`（【面寸法】⇔【辺寸法】、cmd.c:4926）とそのまま
一致**。decomp でもこのトグルは角面のときしか読まれておらず、port が
`c->chamfer==0` のときしか `ch_side` を切り替えさせない（cmd.c:4928）のは
decomp と矛盾しない——**修正不要（これも新たに decomp 確認できた）**。

**新しい発見**：続けて寸法の数値を読むくだり（`DS:0x2883 '=%7.1f'`）を
追うと、**角面・丸面・Ｌ面は別々の記憶領域から最後に使った寸法を読んで
いる**——角面 `[0x103e]/[0x1040]`、丸面 `[0x1042]/[0x1044]`、Ｌ面
`[0x1046]/[0x1048]`（4 バイト＝float 1 個、`lcall 22b2:6cc6` が
`tools/altlift.py` の f32 ロード）。Ｌ面はさらに別の書式（`DS:0x288a
',%7.1f'`）でもう 1 つの値 `[0x104a]/[0x104c]` を続けて表示する——
Ｌ面は寸法が 2 つ（帯の文字列 `DS:0x2837 '(A),(B)辺'`・`DS:0x2855 'Ａ)'`
が裏付ける「(A)辺・(B)辺」の 2 本）。楕円面（`*(int*)0x103a==3`）は
丸面と同じ "半径" ラベル（`DS:0x2850`）を出したあと、丸面と**同じ番地
`[0x1042]`** を読んで絶対値を取り、小さすぎれば `[0x965c]/[0x965e]` の
既定値に差し替える分岐がある（`DS:0x2849 '偏平率'` という別パラメータ
も別途ある）——つまり楕円面の「半径」は丸面の記憶値をそのまま使い回す
作りらしい。

**port との比較**：`src/cmd.h:713` の `gap_chamfer` は **形状をまたいで
共有する 1 個の `double`** でしかない。decomp は角面・丸面・Ｌ面（2 個）
それぞれ別の記憶を持ち、楕円面は丸面の記憶を流用する——明確な構造差。
ただし**この差は今の port では外から観測できない**：数値を打ち込む
唯一の入口（`src/cmd.c:4918` の `item==3` 欄）が `c->chamfer==0`
（角面）のときしか開かないため、丸面・Ｌ面・楕円面の寸法は現状どの
UI 経路からも書き換えられず、`gap_chamfer` は実質「角面用の記憶」としか
使われていない。さらに、二線を押して確定させる本体
（`src/cmd.c:16047`〜 の `if (c->command==8 && !c->chb)` ブロック、
コメントで「面取【角面】」と明記済み）は **`c->chamfer` の値を一切見ず、
常に角面と同じ直線カットの式（`chamfer()`）だけを呼ぶ**——①で丸面・
Ｌ面・楕円面を選んでも、二線を押した結果は角面と同じになる。これは
port の既存コメントがそもそも角面に限定して書かれていた（隠れたバグ
ではなく、既知の未実装の範囲）が、丸面・Ｌ面・楕円面を実装するときに
必要な寸法パラメータの形（半径1個／辺2個／半径+偏平率）を decomp から
確定できたのは今回の収穫。**実装はしていない**——記憶領域の分離だけ
先に直しても外部から検証できず（typing の入口が角面にしか無いので
regression テストで動作の違いを確認できない）、丸面・Ｌ面・楕円面の
実ジオメトリ（弧の挿入・２辺の計算・楕円弧の計算）も今回のスコープでは
読んでいないため、単独のストレージ分離だけ入れるのは検証できない変更
になり見送った。

**結論（10-g 全体）**：3 命令とも入口のオーバーレイ番地はディスパッチャ
表から確定・decomp と一致（面取は元の概観が正しかった、中心線・分割も

  同じ結果になる実装なのか、それとも本物は mark-then-sweep（この関数でビットだけ立てて、
  実際の配列コンパクションは別の共通処理が後で回る）なのかは、**今回は判別できないまま**
  残った（次に読むなら、このビットが立つ条件・下りる条件・どこで読まれて実際に
  描画／保存から外されるかを別途追うこと）。

**結論**：10-c/10-d が残した宿題（①②の在／外判定の式、削除の実体）のうち、
「①②が同じ経路・item-1 だけで分岐する」ことと「範囲取りは共有ルーチンへキャプション
違いで委譲するだけ」の 2 点は decomp で裏取りでき、port の現状（`c->outside = item==2`、
`outside_kind`/`jw_cmd_in_range` による box 判定、`erase_again` の二度押し）と**矛盾する
点は見つからなかった**（＝直す理由は無かった）。一方、在／外判定の具体式（`outside_kind` の
JW_OUT_IN/CROSS/OUT 相当がどこにあるか）と、実際のレコード削除（array compaction か
mark-then-sweep か）は、この関数の中にビット操作としてちらりと見えるだけで、**意味の
確定にはさらに別関数（ビットの読み書き元）を読む必要があり、今回も未解決のまま**。
x87 型崩壊とは別に、この区間は disasm 単体（altlift も同様に decompile できず、
生アセンブリの手読みのみ）で追うしかなく、単体テストで検算できる計算式ではないので
（レジスタの意味がフラグの集合であり、浮動小数の式ではない）、`tools/cc.sh` 等での
裏取りも効かない。次に進むなら、`lcall 0, 0x13f` の実体（どのベクタ／どのセグメントを
指しているか）を先に特定するのが鍵になる。
